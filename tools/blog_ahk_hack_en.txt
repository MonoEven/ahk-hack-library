[b]AutoHotkey Runtime Scanner (ahk-hack)[/b]

Repository: [url=https://github.com/MonoEven/ahk-hack-library]https://github.com/MonoEven/ahk-hack-library[/url]

Bilingual online version: [url=https://monoeven.github.io/ahk-hack-library/]https://monoeven.github.io/ahk-hack-library/[/url]

This library solves one problem: let an AutoHotkey script read the [c]AutoHotkey.exe[/c] that is running it, locate the interpreter's internal tables, and then build on top of them with built-in redirection, expression evaluation, and remote hooking. The implementation embeds x64 machine code in an AutoHotkey v2 file and scans PE structures at runtime.


[b]1. Runtime scanning[/b]

The AutoHotkey 2 interpreter keeps several important tables in the [c].data[/c] section:

- [c]g_BIF[/c]: built-in script functions ([c]Abs[/c], [c]Sin[/c], ...), 0x20 bytes per entry on x64;
- [c]sMdFunc[/c]: typed native functions ([c]MsgBox[/c], [c]WinActivate[/c], ...), 0x28 bytes;
- [c]g_BIV_A[/c]: built-in variables starting with [c]A_[/c] ([c]A_AhkPath[/c], [c]A_YYYY[/c], ...), 0x18 bytes.

Locating a table takes two steps. First the scanner parses the DOS header, NT headers, and section table to get the memory range of each section. Then it checks pointer slots in [c].data[/c] and [c].rdata[/c] against three conditions: the name pointer resolves to a UTF-16 string, the function pointer lands in [c].text[/c], and the records are sorted alphabetically. The contiguous region that satisfies all three is the target table. After that, every entry's RVA, parameter counts, and ID are read out.

Once this logic is in machine code, the same blob runs on 2.0-beta, 2.0.0, 2.0.26, and 2.1-alpha. The same approach was generalized to scan the export tables of arbitrary DLL/EXE modules, enumerating named exports, RVAs, and ordinals.


[b]2. How the machine code is made[/b]

The machine code is written in C, compiled with clang, extracted from the [c].text[/c] section of the COFF object, and embedded into AHK as a hex string:

[codebox=text file=mcode-build]
clang -c -O2 -target x86_64-pc-windows-msvc -ffreestanding \
  -fno-builtin -fno-stack-protector -fno-unwind-tables \
  -fno-asynchronous-unwind-tables -fno-jump-tables scanner.c
[/codebox]

The build script checks relocations in [c].text[/c] and refuses to embed if any relocation escapes the blob. This guarantees the embedded result is self-contained and position-independent.

The machine-code layer ships the following blobs:

- [c]scanner.c[/c]: interpreter table scan;
- [c]export_scanner.c[/c]: generic PE export-table scan;
- [c]inproc_eval.c[/c]: in-process expression evaluation;
- [c]internal_locator.c[/c]: runtime discovery of EvalNative internals;
- [c]mem_script.c[/c]: in-memory [c]TextStream[/c] for EvalScript;
- [c]remote_call_stub.c[/c]: remote-thread call stub;
- [c]remote_eval_stub.c[/c]: remote expression-evaluation stub.

Rebuilding the machine code requires LLVM clang (locally at [c]F:\Tech\LLVM\bin\clang.exe[/c]):

[codebox=text file=rebuild]
python tools\build_mcode.py --embed-only --out ahk_hack_single.ahk
[/codebox]


[b]3. Single-file core[/b]

The scanning core is distilled into one file: [c]ahk_hack_single.ahk[/c]. It contains [c]MCode()[/c], [c]AhkMagic[/c], and all embedded machine code, so it can be copied anywhere and included directly. The repository also includes [c]ahk_hack_demo.ahk[/c], which runs a self-test showing the scan summary, built-in replacement, and Eval.

[b]4. Core usage: scanning and redirection[/b]

[color=#BF4000][b]4.1 Core scanning[/b][/color]

[codebox=autohotkey file=single-file-core-usage]
#Include ahk_hack_single.ahk

AhkMagic.Init()
MsgBox AhkMagic.Summary()

absRva  := AhkMagic.BifRva("Abs")
absAddr := AhkMagic.BifAddr("Abs")

hmod := DllCall("LoadLibraryW", "Str", "D:\path\module.dll", "Ptr")
exports := AhkMagic.ScanExports(hmod)
MsgBox exports.Count
[/codebox]

[color=#BF4000][b]4.2 Built-in redirection[/b][/color]

[codebox=autohotkey file=built-in-pointer-replacement]
#Include ahk_hack_single.ahk

old := AhkMagic.PatchBif("Abs", "Sin")
name := "Abs"
MsgBox %name%(1)              ; table patch: dynamic call returns sin(1)

state := AhkMagic.PatchBifObject(Abs, "Sin")
MsgBox Abs(1)                 ; deep patch: direct call also returns sin(1)
AhkMagic.RestoreBifObject(Abs, state)
AhkMagic.RestoreBif("Abs", old)
[/codebox]

The table patch affects future dynamic lookups. The deep patch rewrites the already-resolved function object's C function pointer, so a direct `Abs(1)` in source also returns `sin(1)`, and is restored to 1 afterwards.

[b]5. In-process Eval[/b]

[color=#BF4000][b]5.1 Expression evaluation[/b][/color]

[codebox=autohotkey file=eval-usage]
#Include ahk_hack_single.ahk

MsgBox AhkMagic.Eval("1 + 2 * 3")          ; 7
MsgBox AhkMagic.Eval("StrLen(`"hello`")")   ; 5
MsgBox AhkMagic.EvalSubprocess("Format(`"{:.2f}`", Sin(1))") ; explicit subprocess
MsgBox AhkMagic.EvalNative("1 + 2 * 3")     ; 7, in-process
MsgBox AhkMagic.EvalNative("2 * 3.5")       ; 7.0, in-process
MsgBox AhkMagic.EvalNative("Abs(-5)")       ; 5, in-process
[/codebox]

[c]EvalNative[/c] builds a temporary [c]Line[/c]/[c]ArgStruct[/c] and calls the interpreter's own [c]ExpressionToPostfix[/c] and [c]ExpandExpression[/c] in this process. It covers literals, operators, global variables, and function calls on the verified builds. Unsupported syntax fails loudly. [c]Eval[/c] tries the in-process pipeline first and falls back to [c]EvalSubprocess[/c] when needed.

[color=#BF4000][b]5.2 Function definitions[/b][/color]

[codebox=autohotkey file=evalscript-function]
#Include ahk_hack_single.ahk

script := "
(
add(a, b) {
    return a + b
}
add(1, 2)
)"
MsgBox AhkMagic.EvalScript(script)          ; 3, in-process
[/codebox]

[color=#BF4000][b]5.3 Class definitions[/b][/color]

[codebox=autohotkey file=evalscript-class]
#Include ahk_hack_single.ahk

classScript := "
(
class Point {
    x := 0
    y := 0
    __New(x, y) {
        this.x := x
        this.y := y
    }
}
Point(1, 2).x
)"
MsgBox AhkMagic.EvalScript(classScript)     ; 1, class loaded and used in-process
MsgBox AhkMagic.EvalNative("Point(1, 2).y") ; 2, class loaded and used in-process
[/codebox]

[c]EvalScript[/c] does not write a temp [c].ahk[/c] file. It encodes the text as UTF-16, builds a [c]TextMem[/c]-compatible [c]TextStream[/c] in a scratch buffer, and passes it directly to [c]LoadIncludedFile(TextStream*)[/c]. Function definitions and class definitions therefore work in-process.

[color=#BF4000][b]5.4 Evaluation pipeline[/b][/color]

[c]How the pipeline evaluates expressions:[/c] AutoHotkey compiles expression strings into postfix [c]ExprTokenType[/c] arrays during script load. [c]Line::ExpressionToPostfix[/c] performs the compilation, [c]PreparseExpressions[/c] pre-compiles expression lines, [c]PreprocessLocalVars[/c] binds local variables, and [c]Line::ExpandExpression[/c] evaluates the postfix. [c]EvalNative()[/c] builds the same temporary [c]Line[/c]/[c]ArgStruct[/c] and calls those functions, so it reuses the interpreter's own grammar and evaluation semantics. [c]EvalScript()[/c] feeds the same [c]LoadIncludedFile(TextStream*, int)[/c] pipeline through an in-memory [c]TextStream[/c]; the parser receives the text from a synthetic stream, and function and class definitions work in-process.

[c]Why dynamic discovery works:[/c] stable error strings are referenced with RIP-relative [c]lea[/c] instructions in every build, so scanning those cross-references and walking back to the prologue yields function addresses. Globals are materialized the same way. Layout offsets are revealed by the running interpreter itself: a one-time probe loads a throwaway function, diffs the live [c]Script[/c] object for [c]mFuncs[/c]/[c]mFuncsCount[/c]/[c]mLastLine[/c], walks the new function's line chain for [c]mJumpLine[/c], and reads parser-state anchors from [c]LoadIncludedFile[/c]'s [c]cmp[/c] prologue. The [c]TextStream[/c] object is built with both [c]mData[/c] regions populated, so no layout choice is needed.

[c]Multi-version compatibility:[/c] the four-version matrix runs the same blob on 2.0-beta.10, 2.0.0, 2.0.26, and 2.1-alpha.30. Stable [c]Line[/c]/[c]ArgStruct[/c]/token offsets have not changed in those builds; everything that changed is discovered at runtime. An unrecognized layout makes the probe throw without guessing, which keeps failures explicit and isolated.

[codebox=text file=source-snippets]
// source/script.h (AutoHotkey v2.1-alpha.30)
ResultType ExpressionToPostfix(ArgStruct &aArg);
LPTSTR ExpandExpression(int aArgIndex, ResultType &aResult, ResultToken *aResultToken,
    LPTSTR &aTarget, LPTSTR &aDerefBuf, size_t &aDerefBufSize,
    LPTSTR aArgDeref[], size_t aExtraSize);

Line *mLastLine;
FuncList mFuncs;
Line *mLineParent = nullptr;
Line *mPendingRelatedLine;
int mExprFuncIndex = INT_MAX;
bool mBackCompatMode = true;
int mClassObjectCount;

// source/TextIO.h
class TextMem : public TextStream {
public:
    struct Buffer { LPVOID mBuffer; DWORD mLength; bool mOwned; };
private:
    Buffer mData;
    LPBYTE mDataPos;
};
[/codebox]

[b]6. Remote hooking[/b]

The target does not require [c]#Include[/c], exported pointers, or callbacks. The attacher reads its memory map, locates the interpreter objects, and starts a remote thread through the OS remote-thread API.

[color=#BF4000][b]6.1 External attach tool[/b][/color]

[c]tools\ahk_remote_attach.py[/c] can read a target process by PID or image name without injecting anything. It uses [c]ReadProcessMemory[/c] to read the PE headers and data sections, reuses the same anchor/run scan to report the three interpreter tables, and can redirect a builtin in the live table or evaluate an expression inside the target.

[codebox=text file=remote]
python tools\ahk_remote_attach.py --pid 1234 --filter Abs,MsgBox,AhkPath
python tools\ahk_remote_attach.py --name AutoHotkey64.exe --redirect Abs Sin
python tools\ahk_remote_attach.py --name AutoHotkey64.exe --eval "1 + 2 * 3"
[/codebox]

[color=#BF4000][b]6.2 AHK hook API[/b][/color]

[c]AttachRemoteByName("AutoHotkey64.exe")[/c] finds the running process by image name, opens it with [c]OpenProcess[/c], reads PE headers and data sections through [c]ReadProcessMemory[/c], scans anchor names and sorted runs to locate the three tables, and returns a map with [c]image_base[/c], [c]table_rva[/c], and entries. [c]AttachRemote(pid)[/c] is the PID-based form of the same scan.

[c]RemoteRedirect(hook, "Abs", "Sin")[/c] reopens the target with write access and writes the destination function pointer into the source entry's [c]fn_ptr[/c] slot. [c]RemoteDeepRedirect(hook, "Abs", "Sin")[/c] goes one level deeper: it scans the target heap for the already-resolved [c]Func[/c] object and patches its [c]mBIF[/c]. This is what changes a function like [c]B()[/c] that directly calls [c]A()[/c].

[color=#BF4000][b]6.3 Hotkey verification[/b][/color]

Remote hooking changes another process's memory, so verification needs the target to write its own results. The target script [c]tests\remote_hook_resident_target.ahk[/c] stays resident; [c]F7[/c] writes the dynamic call [c]%name%(1)[/c] and [c]F8[/c] writes the global [c]x[/c]. The attacher [c]tests\remote_hook_resident_demo.ahk[/c] sends the matching hotkey after each hook step.

[codebox=autohotkey file=remote-hook-attacher]
#Include ahk_hack_single.ahk

; Attacher: tests\remote_hook_resident_demo.ahk
F1:: {
    global hook
    hook := AhkMagic.AttachRemoteByName("AutoHotkey64.exe")
}
F2:: {
    global hook
    AhkMagic.RemoteRedirect(hook, "Abs", "Sin")
    Send "{F7}"          ; activate target hotkey to verify
    Sleep 400
}
F3:: {
    global hook
    AhkMagic.RemoteEval(hook, "x := 1 + 2 * 3")
    Send "{F8}"          ; activate target hotkey to verify
    Sleep 400
}
[/codebox]

[codebox=autohotkey file=remote-resident-target]
; Resident target: tests\remote_hook_resident_target.ahk
#NoTrayIcon
Persistent

pidFile := A_Temp "\ahk_remote_attach_target.pid"
outFile := A_Temp "\ahk_remote_resident.out"
errFile := A_Temp "\ahk_remote_resident.err"
try FileDelete(outFile)
try FileDelete(errFile)
FileAppend(DllCall("GetCurrentProcessId") "`n", pidFile)

x := 0
name := "Abs"

F7:: {
    global name
    global outFile
    try {
        FileAppend("f7=" %name%(1) "`n", outFile)
    } catch as e {
        FileAppend("f7err=" e.Message "`n", outFile)
    }
}

F8:: {
    global x
    global outFile
    FileAppend("f8=" x "`n", outFile)
}
[/codebox]

Start the target, press [c]F1[/c] to attach, then [c]F2[/c] to redirect [c]Abs[/c] to [c]Sin[/c]. When the target receives [c]F7[/c], it writes [c]0.8414709848078965[/c] ([c]Sin(1)[/c]) where it previously wrote [c]1[/c]. Press [c]F3[/c] to evaluate [c]x := 1 + 2 * 3[/c] remotely; the target writes [c]7[/c] when [c]F8[/c] fires.

[color=#BF4000][b]6.4 RemoteEval[/b][/color]

[c]RemoteEval(hook, expr)[/c] copies the internal locator and expression-evaluator blobs plus a tiny thread stub into the target, runs them with [c]CreateRemoteThread[/c], and reads the result back. Basic expressions such as [c]1 + 2 * 3[/c] and [c]2 * 3.5[/c] were verified remotely; string literals and string-returning builtins such as [c]SubStr[/c] and [c]Format[/c] are read back correctly too.

The target needs no special code: no [c]#Include[/c], no exported pointers, no callback, and no embedded metadata. The PID file in the test harness is only test orchestration; [c]tools\ahk_remote_attach.py --name AutoHotkey64.exe[/c] resolves the PID from the image name.

Function-to-function verification: [c]tests\remote_hook_function_target.ahk[/c] defines [c]B_direct()[/c] (direct [c]Abs[/c] call) and [c]B_dynamic()[/c] (dynamic [c]%name%[/c] call). [c]tests\remote_hook_function_demo.ahk[/c] deep redirects [c]Abs -> Sin[/c] and triggers both hotkeys. Both outputs become [c]0.8414709848078965[/c].

[color=#BF4000][b]6.5 RemoteEvalScript[/b][/color]

[c]RemoteEvalScript(hook, text)[/c] loads a multi-line script inside the target through its own script-loading pipeline. The injected thread sets [c]g->CurrentFunc[/c] before [c]PreparseExpressions[/c], so both function and class definitions work.

[codebox=autohotkey file=remote-eval-script]
#Include ahk_hack_single.ahk

hook := AhkMagic.AttachRemoteByName("AutoHotkey64.exe")

script := "
(
add(a, b) {
    return a + b
}
add(1, 2)
)"
MsgBox AhkMagic.RemoteEvalScript(hook, script)   ; 3
[/codebox]

[b]8. Security[/b]

[color=#BF4000]This library allocates executable memory, executes machine code, and reads or writes interpreter internals directly. Use it with reverse-engineering research discipline.[/color]

[c]Is Eval safe? No.[/c] [c]Eval[/c], [c]EvalNative[/c], and [c]EvalScript[/c] execute arbitrary code in the current process with the same privileges as the host script. They are not sandboxes. The in-process path also fabricates interpreter objects, so a wrong layout or state-save mistake can corrupt memory without raising a clean exception. The remote APIs perform the same operations in another AutoHotkey process.

Operations fall into three categories:

- Read-only: [c]Init / Summary / BifRva / BifAddr / ScanExports / AttachRemote[/c]. These do not modify process state; the main risk is compatibility;
- Mutating: [c]PatchBif / RestoreBif / RemoteRedirect / RemoteDeepRedirect / RemoteReplaceFuncBody[/c]. These directly modify interpreter internals and can crash the process if misused. During development this project hit [c]0xC0000374[/c] (heap corruption);
- Executing: [c]Eval / EvalNative / EvalScript / RemoteEval / RemoteEvalScript[/c]. This is equivalent to running arbitrary scripts.

Risks to keep in mind:

- Executable-memory allocation and internal function calls may be flagged by antivirus or EDR;
- Every entry point, global, and layout offset is located at runtime; there is no per-version table, but the target exe still needs a test-suite pass;
- Always restore [c]PatchBif[/c] and remote redirects; do not leave them enabled;
- Never eval untrusted input;
- 32-bit AutoHotkey raises an explicit error.

Recommended workflow: test in a VM or isolated environment, back up the exe, record its SHA256, and only analyze software you are authorized to research. This library is not intended to bypass licensing, DRM, or access controls.

[b]10. Known limitations[/b]

- The machine-code blocks are x64 only; 32-bit AutoHotkey raises an explicit error;
- [c]EvalNative()[/c] runs the interpreter's in-process expression pipeline for literals, operators, global variables, and function calls on all verified builds. [c]Eval()[/c] falls back to [c]EvalSubprocess()[/c] in both script mode and compiled exes built from the regular runtime; an [c]AUTOHOTKEYSC[/c] standalone base would not support [c]/script[/c], so that build should be tested separately;
- UPX/MPRESS compression is verified; third-party packers, VM protectors, or real script encryption still need per-target testing;
- [c]PatchBif()[/c] and [c]RemoteRedirect()[/c] do not retroactively affect already-cached function objects; use [c]PatchBifObject()[/c]/[c]RemoteDeepRedirect()[/c] for that;
- [c]RemoteReplaceFuncBody()[/c] requires both the source and destination functions to be loaded in the target process;
- [c]TraceFunction[/c] currently requires at least two required parameters and rejects optional/ByRef parameters;


[b]11. Closing[/b]

The project ended up settling on scanning: treat the exe as a structured document the program itself can read, scan out the internal map, and experiment on top of that map. In-process eval, remote hooking, script loading, and function tracing now work across 19 verified builds. Future directions include automatic DLL binding generation, deeper object model discovery, and more robust handling of hostile packers.
