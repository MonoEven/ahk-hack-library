1. 为什么要读取正在运行的 exe

AutoHotkey v2 通过内置函数和 A_AhkPath 这类系统变量暴露 脚本可见的表面，但不会公开稳定的 C API 给内部结构。真正有意思的部分 - 内置函数表、带类型签名的原生函数表、A_* 变量表 - 都放在 AutoHotkey64.exe 自己里面。

可执行文件是 PE 镜像。运行在解释器里的脚本本来就能拿到模块基址， 解析镜像头，然后把解释器自己的段当作数据来读。核心思路是：先扫描， 只有明确的操作才改写；扫描结果无法被证明时就直接报错，绝不猜测。

2. PE 地图

64 位 AutoHotkey v2 可执行文件的开头是固定的：MZ DOS 头、由 e_lfanew（偏移 0x3C）指向的 PE\0\0 签名、魔数为 0x20B 的 PE32+ 可选头，以及紧随其后的节表。每个节记录名称、虚拟大小、虚拟地址、 原始大小和属性。 

peOff := NumGet(base, 0x3C, "UInt")
numSections := NumGet(base + peOff + 6, "UShort")
optSize := NumGet(base + peOff + 20, "UShort")
secTable := base + peOff + 24 + optSize

库用 AhkMagic._ModuleSections() 把节表封装成 名称 -> {rva, size, ptr} 的 Map。最常用的是三节：

  • .text：可执行代码，函数指针必须落在这里；
  • .rdata：只读数据，UTF-16 名字通常在这里；
  • .data：读写数据，解释器表在这里构建。

3. 三张解释器内部表

扫描器在 x64 上定位三张记录结构稳定的表：

表 内容 记录步长
g_BIF Abs、Sin 等脚本内置函数 0x20 字节
sMdFunc MsgBox、WinActivate 等带类型签名的原生函数 0x28 字节
g_BIV_A 以 A_ 开头的内置变量 0x18 字节

候选记录必须同时满足三个不变量：名字指针指向 .rdata/.data 中可打印的 UTF-16 字符串， 函数指针落在 .text，并且相邻记录按名字排序。扫描器按 指针对齐的位置遍历，以 Abs、BlockInput、 AhkPath 为锚点，保留满足条件的最长连续区，然后为每条 记录读出 RVA、参数个数和 ID。

这是刻意的签名扫描，不是 RVA 表。同一段机器码已经在 2.0-beta.10、 2.0.0、2.0.26、2.1-alpha.30 上跑通，没有使用任何按版本写死的地址。

4. 重新构建机器码

“重新构建机器码”是把 C 源码变成 ahk_hack_single.ahk 内嵌十六进制常量的可复现过程。这些 blob 不是手写汇编，而是由 tools/build_mcode.py 编译、校验并嵌入的。

lib/mcode/ 下的源码分别是：

源码 用途
scanner.c 定位 g_BIF、sMdFunc、g_BIV_A
export_scanner.c 任意已加载模块的通用 PE 导出表扫描
inproc_eval.c 基于临时 Line 的进程内表达式求值
internal_locator.c EvalNative 内部符号的运行时发现

4.1 编译成 freestanding COFF

clang -c -O2 -target x86_64-pc-windows-msvc -ffreestanding \
  -fno-builtin -fno-stack-protector -fno-unwind-tables \
  -fno-asynchronous-unwind-tables -fno-jump-tables scanner.c

-ffreestanding 表示不依赖 CRT、不链接标准库，也不假设 任何启动状态。-fno-* 选项去掉栈保护、展开元数据和编译器 生成的跳转表，让输出保持小而确定。

4.2 提取 .text 并处理重定位

构建脚本解析 COFF 对象：读节表，取出原始 .text，再遍历 每条重定位记录。它只接受 IMAGE_REL_AMD64_REL32 （类型 4），并且要求目标符号仍然落在 .text 内。其他情况 直接抛错，拒绝嵌入。

原因来自运行时契约。MCode() 把十六进制解码成 AHK Buffer，改成可执行保护后返回；这个 blob 必须是位置无关的： 不能有绝对数据地址、外部导入，也不能引用自己的 .rdata。 如果逃逸的重定位混进来，复制后的字节会去解引用原目标文件里的地址， 而不是当前进程的地址。

4.3 嵌入与验证

python tools\build_mcode.py --embed-only --out ahk_hack_single.ahk

脚本替换四个 MC_*_X64 常量并打印大小。当前源码树完全可 复现：从 lib/mcode/ 重新生成能得到与仓库内完全一致的 常量。目前解释器扫描器是 2559 字节，导出扫描器 297 字节，进程内求值器 1784 字节，内部定位器 1537 字节。

重建后正确的检查不是“看起来像汇编”，而是完整矩阵是否仍然通过，包括 Python 测试、演示脚本和四个解释器上的 AHK 探针。

5. EvalNative：进程内表达式求值

EvalNative() 在 scratch 缓冲区里构造临时 Line 和 ArgStruct，然后直接调用当前进程 解释器自己的表达式函数。没有子进程，所以表达式能看到调用者同一张全局 变量表和同一个模块状态。

第一步是找到这些函数。库在 .text 里搜索对两个稳定错误 字符串的 RIP 相对引用："Missing operand." 和 "Error evaluating expression."，再回退到所在函数开头， 得到 ExpressionToPostfix 与 ExpandExpression。

第二个机器码定位器继续按结构签名发现支撑地址：

  • gScript：ExpressionToPostfix 中出现次数最多的 lea rcx,[rip+disp] 目标；
  • FindVar/FindOrAddVar：六参数 prologue 加空名比较模式；
  • FinalizeExpression：两个主函数之间带标准 ArgStruct prologue 的函数；
  • CRT free：直接调用 ExpressionToPostfix 的调用点之后紧跟的调用；
  • SYM_INVALID：ExpandExpression 内后缀终结立即数。

调用编译器之前，求值器会对 UTF-16 表达式做一次轻量 deref 扫描：跳过 引号字符串，记录标识符起始和长度，并且跳过 . 后面的标识符， 这样 Point(1,2).x 这类成员表达式不会被当成变量。真正的 工作仍由解释器自己的管线完成：ExpressionToPostfix -> FindOrAddVar 解析变量/函数 -> 可选 FinalizeExpression -> ExpandExpression。 

#Include ahk_hack_single.ahk
AhkMagic.Init()

MsgBox AhkMagic.EvalNative("1 + 2 * 3")          ; 7
MsgBox AhkMagic.EvalNative("2 * 3.5")            ; 7.0
MsgBox AhkMagic.EvalNative("Abs(-5)")            ; 5
MsgBox AhkMagic.EvalNative("SubStr(`"abc`", 2)") ; "bc"

myVar := 42
MsgBox AhkMagic.EvalNative("myVar + 1")          ; 43

当前在四个已验证版本上支持字面量、运算符、全局变量和函数调用。不支持 的语法会带着管线状态抛出错误，而不是返回一个猜出来的结果。

6. EvalScript：长文本、函数与类

表达式求值器自己无法定义函数或类。EvalScript() 走另一条 管线：把文本写到临时 .ahk，用 OpenIncludedFile 打开，用 LoadIncludedFile(TextStream*) 加载，对新加入的行执行 PreparseExpressions，再对每个新函数执行 PreprocessLocalVars，最后用 EvalNative() 求值最后一个表达式。

所有入口都在运行时定位：

  • PreparseExpressions：通过 ExpressionToPostfix 的调用者加 cmp byte ptr [rbx], 3/4 模式；
  • PreprocessLocalVars：独特的 movzx 加 cmp byte ptr [rax+0x23], 2 签名；
  • OpenIncludedFile：分别覆盖 2.0 系列和 2.1 的两段 prologue 特征；
  • LoadIncludedFile(TextStream*)：在 OpenIncludedFile 调用者的 cmp eax,3 附近找标准 prologue 的 call；
  • Line::sSourceFileCount：向前回溯找取值合理的小整数的 RIP 相对 load；
  • g 全局：在 PreparseExpressions 调用者里找 mov rax,[rip+disp] 后接偏移 0x28 的 store。

加载前保存脚本状态，在 finally 里恢复：pending 父/关联行、 pending 参数初始化、当前模块、表达式函数状态、类计数。这样多行定义和 类能生效，又不会把临时解析器状态泄漏给调用者。 

script := "
(
add(a, b) {
    return a + b
}
add(1, 2)
)"
MsgBox AhkMagic.EvalScript(script)               ; 3

classScript := "
(
class Point {
    x := 0
    y := 0
    __New(x, y) {
        this.x := x
        this.y := y
    }
}
Point(1, 2).x
)"
MsgBox AhkMagic.EvalScript(classScript)          ; 1

7. 运行时发现与布局常量的边界

“硬编码”有两种含义，这个区别值得说清楚。

维度 状态
表地址（g_BIF、sMdFunc、g_BIV_A） 运行时通过 PE 与签名扫描发现
函数入口（EvalNative 与 EvalScript 管线） 运行时发现，无 RVA 表
全局量（g、gScript、当前行槽、sSourceFileCount） 运行时发现
SYM_INVALID 等枚举值 运行时由内部定位器发现
C++ 结构体字段偏移（Script、ScriptModule、UserFunc、Line、ArgStruct、token） 按版本保留的布局常量，由测试矩阵验证

所以地址层面的答案是肯定的：没有任何函数 RVA、全局地址或表指针来自 按版本列表。剩下的常量描述字段在 C++ 对象里的位置，是更小也更稳定的 兼容面。四条构建的矩阵会逐一覆盖这些入口；如果目标构建的布局不同， 探针会显式失败，而不是猜一个结果。

可选 cnumpy 桥接把同一思路再推进一步：AhkLayout 通过对 存活对象做变更 diff 来发现 Array 的 mItem、 mLength、mCapacity 和 Variant 布局，再用第二组独立探针交叉验证。

8. 完整示例

8.1 表清单

#Include ahk_hack_single.ahk
AhkMagic.Init()

MsgBox AhkMagic.Summary()
for name, info in AhkMagic.bif {
    if name = "Abs" or InStr(name, "Str")
        MsgBox name " rva=0x" Format("{:X}", info["rva"])
}

8.2 通用导出扫描

hmod := DllCall("GetModuleHandle", "Str", "kernel32.dll", "Ptr")
exports := AhkMagic.ScanExports(hmod)
for name in ["VirtualAlloc", "CreateFileW", "ReadProcessMemory"] {
    if exports.Has(name)
        MsgBox name " rva=0x" Format("{:X}", exports[name]["rva"])
}

8.3 内置函数重定向：表指针与对象深替换

old := AhkMagic.PatchBif("Abs", "Sin")
name := "Abs"
MsgBox %name%(1)              ; 后续动态查找返回 sin(1)
AhkMagic.RestoreBif("Abs", old)

state := AhkMagic.PatchBifObject(Abs, "Sin")
MsgBox Abs(1)                 ; 源码里的直接调用也返回 sin(1)
AhkMagic.RestoreBifObject(Abs, state)

PatchBif 改表槽，影响之后发生的动态查找。 PatchBifObject 还会改写已经解析的函数对象里的 C 函数指针， 所以源码里写死的 Abs(1) 也被重定向。上面的例子都会还原。

8.4 表达式求值

MsgBox AhkMagic.Eval("1 + 2 * 3")                  ; 7
MsgBox AhkMagic.Eval("StrLen(`"hello`")")            ; 5
MsgBox AhkMagic.EvalNative("Abs(-5)")                ; 5，进程内
MsgBox AhkMagic.EvalSubprocess("Format(`"{:.2f}`", Sin(1))")

10. 调试与故障

  • 0xC0000005（访问冲突）通常意味着指针或结构偏移错误。 隔离探针、记录版本，并在解引用前检查每个定位出来的地址。
  • 0xC0000374（堆损坏）可能来自解析器状态的保存/恢复顺序 错误。开发中实际遇到过；修复方式是让所有被改写的 Script 字段都在 finally 中恢复。
  • "X not found" 表示定位器无法证明某个签名，这是故意的： 不支持的构建会显式失败，而不是用猜出来的地址继续。
  • 可执行内存分配加内部调用可能被杀毒软件或 EDR 标记。在虚拟机里做实验、 使用一次性解释器，并备份被分析的 exe。

11. 安全与使用规则

这个库会分配可执行内存、执行机器码，并直接读写解释器内部结构。 请按逆向工程研究工具的标准来使用。

操作分三类：

  • 只读：Init、Summary、 BifRva、BifAddr、ScanExports。 不修改进程状态。
  • 修改：PatchBif 和 RestoreBif。用错可能让解释器崩溃。
  • 执行：Eval、EvalNative、 EvalScript。等于在当前进程执行任意代码。

每次实验都要遵守的规则：

  • 不要 eval 未受信任的输入。
  • 每个 PatchBif 都必须还原，不要长期保留重定向。
  • 在信任一个新构建之前，对目标 exe 跑完整测试矩阵。
  • 32 位 AutoHotkey 不支持，会显式报错。
  • 只研究你有权限分析的软件。这个库不用于绕过授权、DRM 或访问控制。

12. 学习路径

  1. 先读 PE 入门资料，并用 ahk_inspect.py 分析一个真实 exe。
  2. 跟读 scanner.c：节区、指针不变量、排序连续区、锚点。
  3. 重建机器码，确认 diff 为空。
  4. 研究 inproc_eval.c 和临时 Line/ArgStruct/ResultToken 布局。
  5. 研究 EvalScript：保存、加载、preparse、preprocess、求值、恢复。
  6. 对照布局表读 AHK v2 源码里的 Script、ScriptModule、UserFunc，并用测试矩阵验证。
