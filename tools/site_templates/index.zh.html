深入 AutoHotkey64.exe：运行时扫描、机器码重建与进程内 Eval

一个 AutoHotkey v2 脚本如何读取正在运行它的解释器、重建内嵌的 x64 机器码，并在不启动子进程的情况下直接使用解释器自己的表达式管线求值。

仓库：MonoEven/ahk-hack-library · 实践项目：cnumpy

本文重点

  • 运行时 PE 解析与解释器内部表扫描。
  • 从 C 源码重建位置无关的机器码。
  • 进程内表达式求值与内存脚本加载。
单文件核心 机器码 C 源码 测试

1. 为什么在运行时扫描

AutoHotkey v2 对外提供的是内置函数和 A_AhkPath 这类系统变量，没有稳定的 C API 可以拿到解释器内部结构。本库用到的三张表 g_BIF、sMdFunc、g_BIV_A 都放在 AutoHotkey64.exe 里。

运行在解释器里的脚本可以用 GetModuleHandle 加 A_AhkPath 拿到模块基址，解析 PE 头，再直接读 .text、.rdata 和 .data。库的做法是先读镜像，只有显式操作才写内存，定位失败时直接抛错。

2. PE 结构

64 位 AutoHotkey v2 可执行文件的头部布局是固定的：MZ DOS 头、由 e_lfanew 指向的 PE\0\0 签名、魔数 0x20B 的 PE32+ 可选头，后面是节表。每个节包含名称、虚拟大小、虚拟地址、原始大小和属性。

peOff := NumGet(base, 0x3C, "UInt")
numSections := NumGet(base + peOff + 6, "UShort")
optSize := NumGet(base + peOff + 20, "UShort")
secTable := base + peOff + 24 + optSize

AhkMagic._ModuleSections() 把节表封装成按节名索引的 Map，每项包含 {rva, size, ptr}。扫描器主要使用三个节：

  • .text 存放可执行代码，是函数指针唯一合法的目标。
  • .rdata 存放只读数据，UTF-16 名字通常在这里。
  • .data 存放可写全局量，解释器表在这里构建。

3. 三张解释器内部表

扫描器在 x64 上定位三张记录布局稳定的表：

表 内容 记录步长
g_BIF Abs、Sin 等脚本内置函数 0x20 字节
sMdFunc MsgBox、WinActivate 等带类型签名的原生函数 0x28 字节
g_BIV_A 以 A_ 开头的内置变量 0x18 字节

每条候选记录必须满足三个条件：名字指针指向 .rdata 或 .data 中的可打印 UTF-16 字符串；函数指针落在 .text；相邻记录按名字排序。扫描器按指针对齐的位置遍历，以 Abs、BlockInput、AhkPath 为锚点，保留满足全部条件的最长连续区，然后读出每条记录的 RVA、参数个数和 ID。

这里用签名扫描而不是 RVA 表，是为了让同一段机器码能直接跑在 2.0-beta.10、2.0.0、2.0.26、2.1-alpha.30 上。

4. 重新构建机器码

“重新构建机器码”指从 lib/mcode/ 里的 C 源码重新生成 ahk_hack_single.ahk 中的十六进制常量。这些 blob 由 tools/build_mcode.py 编译并校验，不是手工写出来的汇编。

源码文件如下：

源码 用途
scanner.c 定位 g_BIF、sMdFunc、g_BIV_A
export_scanner.c 任意已加载模块的通用 PE 导出表扫描
inproc_eval.c 基于临时 Line 的进程内表达式求值
internal_locator.c EvalNative 内部符号的运行时发现
mem_script.c EvalScript 使用的内存 TextStream

4.1 编译成 freestanding COFF

clang -c -O2 -target x86_64-pc-windows-msvc -ffreestanding \
  -fno-builtin -fno-stack-protector -fno-unwind-tables \
  -fno-asynchronous-unwind-tables -fno-jump-tables scanner.c

-ffreestanding 去掉 CRT 启动逻辑和标准库依赖。-fno-* 选项关闭栈保护、展开元数据和编译器生成的跳转表，让输出保持小而确定。

4.2 提取 .text 并处理重定位

构建脚本解析 COFF 对象，取出 .text，逐条检查重定位记录。只有目标符号仍然落在 .text 内的 IMAGE_REL_AMD64_REL32（类型 4）会被接受，其他情况直接终止构建。

原因和运行时放置有关。MCode() 把十六进制字符串解码成 AHK Buffer，改成可执行保护后交给 DllCall 使用。这个 blob 不能有绝对地址、导入或 .rdata 引用，所以能在任意地址运行。一旦有逃出 .text 的重定位，复制后的字节就会指向原目标文件里的地址，而不是当前进程。

4.3 嵌入与验证

python tools\build_mcode.py --embed-only --out ahk_hack_single.ahk

脚本替换五个 MC_*_X64 常量并打印大小。当前从 lib/mcode/ 重新生成可以得到与仓库内完全一致的常量。各 blob 大小为：解释器扫描器 2559 字节、导出扫描器 297 字节、进程内求值器 1784 字节、内部定位器 1537 字节、内存脚本加载器 1016 字节。

重建之后要跑四个解释器上的完整测试矩阵。十六进制本身不适合肉眼审查，测试通过才是有效验证。

5. EvalNative：进程内表达式求值

EvalNative() 分配一块 scratch 缓冲区，构造临时 Line 和 ArgStruct，然后原地调用解释器的表达式管线。整个过程不启动子进程，表达式能直接看到调用者的全局变量表和模块状态。

5.1 为什么这样就能 Eval

AutoHotkey 不会直接求值一段表达式字符串。脚本加载时，每个表达式行会由 Line::ExpressionToPostfix 编译成后缀 ExprTokenType 数组，解析变量和函数引用，之后由 Line::ExpandExpression 执行。EvalNative() 构造的临时 Line/ArgStruct 与解析器会生成的完全一致，然后调用同一组函数。结果不是重新实现一遍 AHK 语义，而是让解释器自己的表达式管线运行在一条合成行上。运算符优先级、字符串转义、内置函数调用和全局变量解析都与编译后的脚本行完全一致。

// source/script.h (AutoHotkey v2.1-alpha.30)
ResultType ExpressionToPostfix(ArgStruct &aArg);
ResultType ExpressionToPostfix(ArgStruct &aArg, ExprTokenType *&aInfix);
ResultType FinalizeExpression(ArgStruct &aArg);
LPTSTR ExpandExpression(int aArgIndex, ResultType &aResult, ResultToken *aResultToken,
    LPTSTR &aTarget, LPTSTR &aDerefBuf, size_t &aDerefBufSize,
    LPTSTR aArgDeref[], size_t aExtraSize);

第一步是定位函数。库在 .text 里搜索对两个稳定错误字符串 "Missing operand." 和 "Error evaluating expression." 的 RIP 相对引用，再回退到所在函数开头，得到 ExpressionToPostfix 和 ExpandExpression。

其余支撑地址由第二个机器码定位器发现：

  • gScript：ExpressionToPostfix 中出现次数最多的 lea rcx,[rip+disp] 目标。
  • FindVar/FindOrAddVar：六参数 prologue 加空名比较模式。
  • FinalizeExpression：两个主函数之间带标准 ArgStruct prologue 的函数。
  • CRT free：直接调用 ExpressionToPostfix 的调用点之后紧跟的调用。
  • SYM_INVALID：ExpandExpression 内的后缀终结立即数。

调用 ExpressionToPostfix 之前，求值器会扫描 UTF-16 表达式并标记需要解析的标识符。引号字符串和 . 后面的标识符会被跳过，所以 Point(1,2).x 这类成员表达式不会被当成变量。后缀生成之后，FindOrAddVar 解析变量和函数引用；构建里有独立 FinalizeExpression 时先执行它；最后 ExpandExpression 求值。

#Include ahk_hack_single.ahk
AhkMagic.Init()

MsgBox AhkMagic.EvalNative("1 + 2 * 3")          ; 7
MsgBox AhkMagic.EvalNative("2 * 3.5")            ; 7.0
MsgBox AhkMagic.EvalNative("Abs(-5)")            ; 5
MsgBox AhkMagic.EvalNative("SubStr(`"abc`", 2)") ; "bc"

myVar := 42
MsgBox AhkMagic.EvalNative("myVar + 1")          ; 43

已验证的版本支持字面量、运算符、全局变量和函数调用。不支持的输入会带着管线状态抛出错误。

6. EvalScript：解析器框架与内存加载

6.1 AutoHotkey 如何解析脚本

脚本加载是一条管线。Script::LoadFromFile 打开主文件；OpenIncludedFile 创建 TextStream；LoadIncludedFile(TextStream*, int) 通过 GetLine/GetLineContinuation 逐行读取，分类每行（指令、热键、标签、类、表达式），再通过 AddLine/ParseAndAddLine 创建 Line 对象。表达式行由 ExpressionToPostfix 编译成 ExprTokenType 数组；PreparseExpressions 在加载期预编译表达式行；PreprocessLocalVars 绑定函数体内的局部变量。函数定义注册到 Script::mFuncs，每个 UserFunc 保存指向函数体的 mJumpToLine 指针。

// source/script.h (AutoHotkey v2.1-alpha.30)，EvalScript 用到的 Script 字段
Line *mLastLine;
FuncList mFuncs;
ScriptModule *mCurrentModule = &mBuiltinModule;
ScriptModule *mLastModule = &mDefaultModule;
Line *mLineParent = nullptr;
Line *mPendingRelatedLine;
Line *mLastParamInitializer;
LPCTSTR mPendingHotkey = nullptr;
int mExprFuncIndex = INT_MAX;
bool mNextLineIsFunctionBody;
bool mIgnoreNextBlockBegin;
bool mBackCompatMode = true;
int mClassObjectCount;

这就是 EvalScript() 能在进程内定义函数和类的原因：它喂给 LoadIncludedFile 同一条管线，只是文本来自内存 TextStream 而不是磁盘文件。解析器不需要知道文本来自哪里。

// source/script.cpp (AutoHotkey v2.1-alpha.30)，已省略
ResultType Script::LoadIncludedFile(TextStream *fp)
{
    int source_file_index = mCurrFileIndex;
    bool blocks_previously_open = mLineParent || mClassObjectCount;
    auto module_previously_open = mCurrentModule;
    bool caller_backcompatmode = mBackCompatMode;
    LineBuffer buf, next_buf;
    ...
    while (buf_length != -1)
    {
        if (!GetLineContinuation(fp, buf, next_buf, phys_line_number, has_continuation_section))
            return FAIL;
        ...
    }
}

表达式求值本身无法定义函数或类。EvalScript() 改走解释器的 include 流程，但直接从内存加载：文本编码为 UTF-16，在 scratch 缓冲区里构造一个最小的 TextMem 兼容 TextStream，直接交给 LoadIncludedFile(TextStream*)，不创建临时 .ahk 文件。新行随后执行 PreparseExpressions，新函数执行 PreprocessLocalVars，最后用 EvalNative() 求值最后一个非声明行。

这些入口都在运行时定位：

  • PreparseExpressions：通过 ExpressionToPostfix 的调用者加 cmp byte ptr [rbx], 3/4 模式定位。
  • PreprocessLocalVars：用 movzx 加 cmp byte ptr [rax+0x23], 2 签名定位。
  • OpenIncludedFile：作为 LoadIncludedFile(TextStream*) 的定位指纹，用分别覆盖 2.0 系列和 2.1 的两段 prologue 特征定位。
  • LoadIncludedFile(TextStream*)：在 OpenIncludedFile 调用者的 cmp eax,3 附近定位。
  • Line::sSourceFileCount：向前回溯找取值合理的小整数的 RIP 相对 load。
  • g 全局：在 PreparseExpressions 调用者里找 mov rax,[rip+disp] 后接偏移 0x28 的 store。

内存 TextStream 会同时填充两个可能的 mData 区域，所以加载器不需要区分 2.0 与 2.1 的布局。加载前保存脚本状态，并在 finally 中恢复：pending 父/关联行、pending 参数初始化、当前模块、表达式函数状态和类计数。临时解析器状态不会泄漏给调用者。

script := "
(
add(a, b) {
    return a + b
}
add(1, 2)
)"
MsgBox AhkMagic.EvalScript(script)               ; 3

classScript := "
(
class Point {
    x := 0
    y := 0
    __New(x, y) {
        this.x := x
        this.y := y
    }
}
Point(1, 2).x
)"
MsgBox AhkMagic.EvalScript(classScript)          ; 1
MsgBox AhkMagic.EvalNative("Point(1, 2).y")      ; 2，类已加载并在进程内使用

7. 运行时发现与布局常量

“硬编码”需要先定义清楚。本库现在已经没有任何按版本维护的表。表地址、函数入口、全局量和枚举值都在运行时发现；EvalScript 用到的 Script 字段偏移也是运行时发现：一次性探针从内存加载一个函数，diff 存活 Script 对象找到 mFuncs、mFuncsCount、mLastLine，沿新函数的行链找到 mJumpLine，再从 LoadIncludedFile 的 prologue 读取解析器状态锚点。Line/ArgStruct/token 这类稳定偏移是固定常量，在已验证的构建中没有变化。

维度 状态
表地址（g_BIF、sMdFunc、g_BIV_A） 运行时通过 PE 与签名扫描发现
函数入口（EvalNative 与 EvalScript 管线） 运行时发现，无 RVA 表
全局量（g、gScript、当前行槽、sSourceFileCount） 运行时发现
SYM_INVALID 等枚举值 运行时由内部定位器发现
Script/UserFunc/TextStream 布局偏移 运行时通过探针 diff 与机器码锚点发现

探针每个进程只运行一次，结束后恢复 Script 对象，不会留下隐藏测试函数。如果目标构建的布局不同，探针会显式失败，不会用猜出来的偏移继续。

7.1 为什么这些方法能读取版本参数

地址能被发现，是因为稳定字符串形成了稳定交叉引用。解释器在每次构建里都用 RIP 相对的 lea 指令引用 "Missing operand." 这类错误字符串；沿引用回退到函数开头就能找到所属函数。全局变量同理：编译器用 lea reg,[rip+disp] 取全局地址，统计并过滤这些引用就能得到 g、gScript 和当前行槽。

// source/script.h (AutoHotkey v2.1-alpha.30)
class UserFunc : public Func {
public:
    Line *mJumpToLine = nullptr;
    ...
};

// source/TextIO.h
class TextMem : public TextStream {
public:
    struct Buffer {
        LPVOID mBuffer;
        DWORD mLength;
        bool mOwned;
    };
private:
    Buffer mData;
    LPBYTE mDataPos;
};

布局偏移是另一个问题。与其写死，探针让运行中的解释器自己暴露它们：加载一个一次性函数，diff 存活 Script 对象找到 mFuncs、mFuncsCount、mLastLine，再沿新函数的行链找到 mJumpLine。解析器状态锚点从 LoadIncludedFile prologue 里的 cmp 指令读取。TextStream 布局干脆不做选择：两个 mData 区域同时填充，同一个对象在两种布局下都能工作。这些方法依赖的是解释器的结构不变量，不是按版本写死的魔数。

7.2 多版本兼容

兼容性是能被测试证明的结论，不是假设。四版本矩阵用同一份 blob 跑 2.0-beta.10、2.0.0、2.0.26、2.1-alpha.30。Line/ArgStruct/token 这些稳定偏移在这些构建中没有变化；变化的都改为运行时发现。如果未来某个构建改了无法识别的布局，探针或定位器会直接抛错，而不是带着猜出来的偏移继续。这是设计的失败模式：显式、隔离、容易调试。

可选 cnumpy 桥接把同一思路用在 AHK Array 对象上。AhkLayout 通过 diff 存活对象发现 mItem、mLength、mCapacity 和 Variant 布局，再用第二组独立探针交叉验证。

Ahk2Exe 打包不会让进程内 Eval 失效。编译出的 exe 内嵌同一个 AutoHotkey 运行时，Init、EvalNative、EvalScript 照常工作；四个版本都用 AutoHotkey64.exe 作为 Ahk2Exe base 验证过。EvalSubprocess 也能正常工作：编译 exe 通过 /script 重新进入解释器模式来执行临时脚本。UPX 和 MPRESS 压缩也验证过；压缩包会改写节名，扫描器会退回到基于内容的节分类。正在运行的进程也可以通过 tools/ahk_remote_attach.py 按 PID 从外部扫描同一组表，无需注入，并支持改写运行中的内置函数表。

AttachRemote(pid)把同一套扫描做成 AHK Hook API：OpenProcess加ReadProcessMemory、解析 PE 节、用锚点和连续记录定位三张表。RemoteRedirect(hook, "Abs", "Sin")再把新函数指针写进运行中的 BIF 槽。

RemoteDeepRedirect(hook, "Abs", "Sin")再深一层：扫描目标堆里已解析的 Func 对象并改写 mBIF，让直接调用 A() 的 B() 也跟着变化。

F1:: {
    global hook
    hook := AhkMagic.AttachRemoteByName("AutoHotkey64.exe")
}
F2:: {
    global hook
    AhkMagic.RemoteRedirect(hook, "Abs", "Sin")
    Send "{F7}"          ; 触发目标热键校验
    Sleep 400
}
F3:: {
    global hook
    AhkMagic.RemoteEval(hook, "x := 1 + 2 * 3")
    Send "{F8}"          ; 触发目标热键校验
    Sleep 400
}

RemoteEval(hook, expr)把 Hook 再推进一步：向目标进程注入线程 stub、内部定位器和求值 blob，用 CreateRemoteThread 执行并读回结果。

RemoteEvalScript(hook, text)现在可以通过目标脚本加载管线在目标里加载多行脚本，包括函数和 class 定义。注入线程会在 PreparseExpressions 前设置 g->CurrentFunc，让使用 Super 的 class 方法正确解析。

script := "
(

    return a + b
}
add(1, 2)
)"
MsgBox AhkMagic.RemoteEvalScript(hook, script)   ; 3

10. 调试与故障

  • 0xC0000005 通常意味着指针或结构偏移错误。隔离探针、记录版本，并在解引用前确认每个定位出来的地址。
  • 0xC0000374 可能来自解析器状态的保存或恢复顺序错误。开发中实际遇到过；修复方式是让所有被改写的 Script 字段都在 finally 中恢复。
  • "X not found" 表示定位器签名没有匹配。这是有意设计：不支持的构建直接失败，不会用猜出来的地址继续。
  • 可执行内存分配和内部调用可能被杀毒软件或 EDR 标记。在虚拟机里测试、使用一次性解释器，并备份被分析的 exe。

11. 安全与使用规则

11.1 Eval 安全吗

不安全。Eval、EvalNative、EvalScript 会在当前进程里以宿主脚本相同的权限执行任意代码，不是沙箱。进程内路径还会伪造解释器对象，布局错误或状态保存失误可能直接损坏内存，而不是抛出一个干净的异常。请把每一个被求值的字符串都当作拥有完整进程权限的脚本。

这个库会分配可执行内存、执行机器码，并直接读写解释器内部结构。请按逆向工程研究工具的标准来使用。

操作分三类：

  • 只读：Init、Summary、BifRva、BifAddr、ScanExports。不修改进程状态。
  • 修改：PatchBif 和 RestoreBif。用错可能让解释器崩溃。
  • 执行：Eval、EvalNative、EvalScript。等于在当前进程执行任意代码。

每次实验都要遵守的规则：

  • 不要 eval 未受信任的输入。
  • 每个 PatchBif 都必须还原，不要长期保留重定向。
  • 在信任一个新构建之前，对目标 exe 跑完整测试矩阵。
  • 32 位 AutoHotkey 不支持，会显式报错。
  • 只研究你有权限分析的软件。这个库不用于绕过授权、DRM 或访问控制。

12. 学习路径

  1. 先读 PE 入门资料，并用 ahk_inspect.py 分析一个真实 exe。
  2. 跟读 scanner.c：节区、指针不变量、排序连续区、锚点。
  3. 重建机器码，确认 diff 为空。
  4. 研究 inproc_eval.c 和临时 Line/ArgStruct/ResultToken 布局。
  5. 研究 EvalScript：保存、加载、preparse、preprocess、求值、恢复。
  6. 对照布局表读 AHK v2 源码里的 Script、ScriptModule、UserFunc，并用测试矩阵验证。
