1. Why read the running executable

AutoHotkey v2 exposes the script-facing surface through built-ins and system variables such as A_AhkPath, but it does not publish a stable C API for its internals. The interesting structures - the built-in function table, the typed native-function table, and the A_* variable table - live inside AutoHotkey64.exe itself.

The executable is a PE image. A script already running inside the interpreter can obtain the module base, parse the image headers, and treat the interpreter's own sections as data. That is the core idea: scan first, mutate only when a deliberate operation asks for it, and fail loudly when a scan cannot prove what it found.

2. The PE map

Every 64-bit AutoHotkey v2 executable starts with the same fixed landmarks: the MZ DOS header, the PE signature PE\0\0 at the offset stored in e_lfanew, and a PE32+ optional header with magic 0x20B. The section table follows the optional header. Each section contributes a name, virtual size, virtual address, raw size, and characteristics. 

peOff := NumGet(base, 0x3C, "UInt")
numSections := NumGet(base + peOff + 6, "UShort")
optSize := NumGet(base + peOff + 20, "UShort")
secTable := base + peOff + 24 + optSize

The library wraps this in AhkMagic._ModuleSections(), returning a map from section name to {rva, size, ptr}. Three sections matter most:

  • .text: executable code, where function pointers must land;
  • .rdata: read-only data, where UTF-16 names usually live;
  • .data: read-write data, where the interpreter tables are built.

3. The three interpreter tables

The scanner targets three tables with stable record shapes on x64:

Table Contents Record stride
g_BIF script-visible built-ins such as Abs and Sin 0x20 bytes
sMdFunc typed native functions such as MsgBox and WinActivate 0x28 bytes
g_BIV_A built-in variables beginning with A_ 0x18 bytes

A candidate record must satisfy three invariants: its name pointer resolves to a printable UTF-16 string in .rdata or .data, its function pointer resolves into .text, and its neighbors in the table stay sorted by name. The scanner walks pointer-aligned slots, anchors on known entries (Abs, BlockInput, AhkPath), and keeps the longest run that satisfies the invariants. The result is a table address plus one entry of metadata per record: RVA, parameter count, and ID.

This is deliberately a signature scan rather than an RVA table. The same machine-code blob has run on 2.0-beta.10, 2.0.0, 2.0.26, and 2.1-alpha.30 without a single per-version address.

4. Rebuilding the machine code

"Rebuilding the machine code" is the reproducible process that turns C sources into the hex constants embedded in ahk_hack_single.ahk. The blobs are not handwritten assembly. They are compiled, checked, and embedded by tools/build_mcode.py.

The sources under lib/mcode/ are:

Source Purpose
scanner.c locates g_BIF, sMdFunc, and g_BIV_A
export_scanner.c generic PE export-table scan for any loaded module
inproc_eval.c in-process expression evaluator over a temporary Line
internal_locator.c runtime discovery of EvalNative internals

4.1 Compile to a freestanding COFF object

clang -c -O2 -target x86_64-pc-windows-msvc -ffreestanding \
  -fno-builtin -fno-stack-protector -fno-unwind-tables \
  -fno-asynchronous-unwind-tables -fno-jump-tables scanner.c

-ffreestanding means no CRT entry, no standard-library dependency, and no assumptions about startup state. The -fno-* flags keep the output small and free of stack cookies, unwind metadata, and compiler-generated jump tables.

4.2 Extract .text and resolve relocations

The build script parses the COFF object: it reads the section table, extracts the raw .text bytes, and walks every relocation. It accepts only IMAGE_REL_AMD64_REL32 (type 4), and only when the target symbol resolves back into .text. Anything else raises an error and refuses to embed.

The reason is the runtime contract. MCode() decodes the hex string into an AHK Buffer, changes its protection to executable, and returns it. The blob must be position-independent: no absolute data addresses, no external imports, no references to its own .rdata. If an escaping relocation slipped through, the copied bytes would dereference an address that belongs to the original object file, not to the running process.

4.3 Embed and verify

python tools\build_mcode.py --embed-only --out ahk_hack_single.ahk

The script replaces the four MC_*_X64 constants and prints the blob sizes. On the current tree the build is reproducible: regenerating from lib/mcode/ reproduces the exact constants already checked in. Current sizes are 2559 bytes for the interpreter scanner, 297 bytes for the export scanner, 1784 bytes for the in-process evaluator, and 1537 bytes for the internal locator.

After any rebuild, the correct check is not "does it look like assembly" but "does the full matrix still pass". That includes the Python tests, the demo, and the four-interpreter AHK probes.

5. EvalNative: in-process expression evaluation

EvalNative() builds a temporary Line and ArgStruct in a scratch buffer, then calls the running interpreter's own expression functions. No child process is started, so the expression sees the same global variable table and the same module state as the caller.

The first problem is finding the functions. The library searches .text for RIP-relative references to two stable error strings, "Missing operand." and "Error evaluating expression.", then walks back to the enclosing function starts. Those become ExpressionToPostfix and ExpandExpression.

A second machine-code locator then discovers the supporting addresses by structural signatures:

  • gScript: the most frequent lea rcx,[rip+disp] target inside ExpressionToPostfix;
  • FindVar/FindOrAddVar: a six-argument prologue plus a null-name comparison pattern;
  • FinalizeExpression: the standard ArgStruct prologue between the two main functions;
  • CRT free: the call reached immediately after the direct caller of ExpressionToPostfix;
  • SYM_INVALID: the postfix terminator immediate found inside ExpandExpression.

Before calling the compiler, the evaluator runs a lightweight deref scan over the UTF-16 expression. It skips quoted strings, records identifier starts and lengths, and - importantly - skips identifiers that follow a ., so member expressions such as Point(1,2).x are not mistaken for variables. The interpreter's own pipeline then does the real work: ExpressionToPostfix, variable/function resolution via FindOrAddVar, optional FinalizeExpression, and finally ExpandExpression. 

#Include ahk_hack_single.ahk
AhkMagic.Init()

MsgBox AhkMagic.EvalNative("1 + 2 * 3")          ; 7
MsgBox AhkMagic.EvalNative("2 * 3.5")            ; 7.0
MsgBox AhkMagic.EvalNative("Abs(-5)")            ; 5
MsgBox AhkMagic.EvalNative("SubStr(`"abc`", 2)") ; "bc"

myVar := 42
MsgBox AhkMagic.EvalNative("myVar + 1")          ; 43

The current surface is literals, operators, global variables, and function calls on all four verified builds. Unsupported syntax throws an error with the pipeline status instead of returning a guessed result.

6. EvalScript: long text, functions, and classes

An expression evaluator cannot define functions or classes by itself. EvalScript() therefore walks a different pipeline: it writes the text to a temporary .ahk file, asks the interpreter to open it through OpenIncludedFile, loads it through LoadIncludedFile(TextStream*), prepares the newly added lines with PreparseExpressions, and runs PreprocessLocalVars for each new function. The last non-declaration line is then evaluated in-process with EvalNative().

All of those entry points are located at runtime:

  • PreparseExpressions is found through callers of ExpressionToPostfix combined with cmp byte ptr [rbx], 3/4 patterns;
  • PreprocessLocalVars uses its unique movzx plus cmp byte ptr [rax+0x23], 2 signature;
  • OpenIncludedFile uses two build-dependent prologue needles covering the 2.0 line and 2.1;
  • LoadIncludedFile(TextStream*) is found through a cmp eax,3 site in the callers of OpenIncludedFile;
  • Line::sSourceFileCount is discovered from a backward RIP-relative load with a plausible small count;
  • the g global is discovered inside callers of PreparseExpressions via its mov rax,[rip+disp] followed by a store into offset 0x28.

The script state is saved before loading and restored in a finally block: pending parent/related lines, pending parameter initializers, current module, expression-function state, and class count. That is what makes multi-line definitions and classes work without leaking temporary parser state into the caller. 

script := "
(
add(a, b) {
    return a + b
}
add(1, 2)
)"
MsgBox AhkMagic.EvalScript(script)               ; 3

classScript := "
(
class Point {
    x := 0
    y := 0
    __New(x, y) {
        this.x := x
        this.y := y
    }
}
Point(1, 2).x
)"
MsgBox AhkMagic.EvalScript(classScript)          ; 1

7. Runtime discovery versus layout constants

"Hardcoded" can mean two different things, and the distinction is worth stating precisely.

Axis Status
Table addresses (g_BIF, sMdFunc, g_BIV_A) Runtime-discovered by PE + signature scan
Function entry points (EvalNative and EvalScript pipelines) Runtime-discovered, no RVA table
Globals (g, gScript, current-line slot, sSourceFileCount) Runtime-discovered
Enum values such as SYM_INVALID Runtime-discovered by the internal locator
C++ struct field offsets (Script, ScriptModule, UserFunc, Line, ArgStruct, tokens) Per-version layout constants, validated by the test matrix

So the answer at the address level is yes: no function RVA, no global address, and no table pointer is read from a per-version list. The remaining constants describe how fields sit inside C++ objects. They are a smaller and more stable surface, and every entry is exercised by the four-build matrix. If a target build differs in layout, the probes fail with an explicit error rather than guessing.

The optional cnumpy bridge takes the same philosophy one step further for AHK Array objects: AhkLayout discovers mItem, mLength, mCapacity, and the Variant layout by mutation diffing on live objects, then cross-validates with a second independent probe set.

8. Complete examples

8.1 Table inventory

#Include ahk_hack_single.ahk
AhkMagic.Init()

MsgBox AhkMagic.Summary()
for name, info in AhkMagic.bif {
    if name = "Abs" or InStr(name, "Str")
        MsgBox name " rva=0x" Format("{:X}", info["rva"])
}

8.2 Generic export scan

hmod := DllCall("GetModuleHandle", "Str", "kernel32.dll", "Ptr")
exports := AhkMagic.ScanExports(hmod)
for name in ["VirtualAlloc", "CreateFileW", "ReadProcessMemory"] {
    if exports.Has(name)
        MsgBox name " rva=0x" Format("{:X}", exports[name]["rva"])
}

8.3 Built-in redirection, table and object

old := AhkMagic.PatchBif("Abs", "Sin")
name := "Abs"
MsgBox %name%(1)              ; dynamic lookup now returns sin(1)
AhkMagic.RestoreBif("Abs", old)

state := AhkMagic.PatchBifObject(Abs, "Sin")
MsgBox Abs(1)                 ; direct call now returns sin(1)
AhkMagic.RestoreBifObject(Abs, state)

PatchBif changes the table slot used by future dynamic lookups. PatchBifObject additionally rewrites the already-resolved function object's C function pointer, so a direct Abs(1) in source is redirected too. Both are restored in the example above.

8.4 Expression eval

MsgBox AhkMagic.Eval("1 + 2 * 3")                  ; 7
MsgBox AhkMagic.Eval("StrLen(`"hello`")")            ; 5
MsgBox AhkMagic.EvalNative("Abs(-5)")                ; 5, in-process
MsgBox AhkMagic.EvalSubprocess("Format(`"{:.2f}`", Sin(1))")

10. Debugging and failure modes

  • 0xC0000005 (access violation) usually means a wrong pointer or struct offset. Isolate the probe, record the version, and check every located address before dereferencing.
  • 0xC0000374 (heap corruption) is possible when parser state is saved or restored in the wrong order. The project hit it during development; the fix was to restore every touched Script field in a finally block.
  • "X not found" errors mean a locator could not prove a signature. They are intentional: an unsupported build fails loudly instead of scanning with a guessed address.
  • Executable allocation plus internal calls can be flagged by antivirus or EDR. Run experiments in a VM, use a disposable interpreter, and keep the analyzed exe backed up.

11. Security and usage rules

This library allocates executable memory, executes machine code, and reads or writes interpreter internals directly. Treat it as a reverse-engineering research tool.

Operations fall into three categories:

  • Read-only: Init, Summary, BifRva, BifAddr, ScanExports. These do not modify process state.
  • Mutating: PatchBif and RestoreBif. Wrong usage can crash the interpreter.
  • Executing: Eval, EvalNative, and EvalScript. This is arbitrary code execution in the current process.

Rules that apply to every experiment:

  • Never evaluate untrusted input.
  • Restore every PatchBif; do not leave redirection enabled.
  • Run the full test suite against the exact target exe before relying on a new build.
  • 32-bit AutoHotkey is not supported and raises an explicit error.
  • Only analyze software you are authorized to research. This is not a tool for bypassing licensing, DRM, or access controls.

12. Learning path

  1. Read a PE primer and inspect a real exe with ahk_inspect.py before touching the AHK side.
  2. Trace scanner.c: sections, pointer invariants, sorted runs, anchor names.
  3. Rebuild the machine code and verify the diff is empty.
  4. Study inproc_eval.c and the temporary Line/ArgStruct/ResultToken layout.
  5. Study EvalScript: save, load, preparse, preprocess, evaluate, restore.
  6. Read the AHK v2 source structures that appear in the layout table (Script, ScriptModule, UserFunc) and correlate them with the test matrix.
