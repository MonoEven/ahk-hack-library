1. Why scan at runtime

AutoHotkey v2 exposes the script-facing surface through built-ins and system variables such as A_AhkPath, but it does not provide a stable C API for interpreter internals. The tables used by this library, g_BIF, sMdFunc, and g_BIV_A, live inside AutoHotkey64.exe itself.

A script running inside the interpreter can call GetModuleHandle with A_AhkPath, parse the PE headers, and inspect .text, .rdata, and .data directly. The library reads the image first, mutates only through explicit operations, and lets locator failures surface as errors.

2. The PE map

Every x64 AutoHotkey v2 executable starts with the same fixed layout: an MZ DOS header, the PE signature PE\0\0 at the offset stored in e_lfanew, and a PE32+ optional header with magic 0x20B. The section table follows the optional header; each entry records a name, virtual size, virtual address, raw size, and characteristics.

peOff := NumGet(base, 0x3C, "UInt")
numSections := NumGet(base + peOff + 6, "UShort")
optSize := NumGet(base + peOff + 20, "UShort")
secTable := base + peOff + 24 + optSize

AhkMagic._ModuleSections() wraps this into a Map keyed by section name, with {rva, size, ptr} per section. Three sections are used by the scanner:

  • .text contains executable code, so it is the only valid target for function pointers.
  • .rdata holds read-only data, where UTF-16 names usually live.
  • .data holds writable globals, where the interpreter tables are built.

3. The three interpreter tables

The scanner looks for three tables whose record layout is stable on x64:

Table Contents Record stride
g_BIF script-visible built-ins such as Abs and Sin 0x20 bytes
sMdFunc typed native functions such as MsgBox and WinActivate 0x28 bytes
g_BIV_A built-in variables beginning with A_ 0x18 bytes

Every candidate record has to pass three checks. The name pointer must resolve to a printable UTF-16 string in .rdata or .data. The function pointer must resolve into .text. Neighboring records must remain sorted by name. The scanner walks pointer-aligned slots, anchors on Abs, BlockInput, and AhkPath, and keeps the longest run that satisfies all three checks. It then reads each record's RVA, parameter counts, and ID.

Signature scanning was chosen over an RVA table so that the same blob can run on 2.0-beta.10, 2.0.0, 2.0.26, and 2.1-alpha.30.

4. Rebuilding the machine code

"Rebuilding the machine code" means regenerating the hex constants embedded in ahk_hack_single.ahk from the C sources in lib/mcode/. The blobs are compiled and checked by tools/build_mcode.py, not transcribed by hand.

The sources are:

Source Purpose
scanner.c locates g_BIF, sMdFunc, and g_BIV_A
export_scanner.c generic PE export-table scan for any loaded module
inproc_eval.c in-process expression evaluator over a temporary Line
internal_locator.c runtime discovery of EvalNative internals

4.1 Compile to a freestanding COFF object

clang -c -O2 -target x86_64-pc-windows-msvc -ffreestanding \
  -fno-builtin -fno-stack-protector -fno-unwind-tables \
  -fno-asynchronous-unwind-tables -fno-jump-tables scanner.c

-ffreestanding removes CRT startup and standard-library assumptions. The -fno-* flags disable stack protectors, unwind tables, and compiler-generated jump tables, which keeps the output small and deterministic.

4.2 Extract .text and resolve relocations

The build script parses the COFF object, extracts the .text bytes, and walks every relocation record. It accepts IMAGE_REL_AMD64_REL32 (type 4) only when the target symbol stays inside .text. Any other relocation aborts the build.

The reason is runtime placement. MCode() decodes the hex string into an AHK Buffer, changes its protection to executable, and returns it for DllCall. The blob has no absolute addresses, imports, or .rdata references, so it can run at any address. A relocation that escapes .text would make the copied bytes point back into the original object file instead of the current process.

4.3 Embed and verify

python tools\build_mcode.py --embed-only --out ahk_hack_single.ahk

The script replaces the four MC_*_X64 constants and prints the blob sizes. Regenerating from lib/mcode/ currently reproduces the checked-in constants exactly. The sizes are 2559 bytes for the interpreter scanner, 297 for the export scanner, 1784 for the in-process evaluator, and 1537 for the internal locator.

After a rebuild, run the test suite across the four interpreters. That is the actual verification; the hex strings themselves are not meant to be reviewed by eye.

5. EvalNative: in-process expression evaluation

EvalNative() allocates a scratch buffer, builds a temporary Line and ArgStruct, and calls the interpreter's expression pipeline in place. No child process is involved, so the expression resolves against the caller's global variable table and module state.

The first step is locating the functions. The library scans .text for RIP-relative references to two stable error strings, "Missing operand." and "Error evaluating expression.", then walks backward to the enclosing function starts. Those functions are ExpressionToPostfix and ExpandExpression.

Supporting addresses come from a second machine-code locator:

  • gScript: the most frequent lea rcx,[rip+disp] target inside ExpressionToPostfix.
  • FindVar/FindOrAddVar: a six-argument prologue plus a null-name comparison pattern.
  • FinalizeExpression: the standard ArgStruct prologue between the two main functions.
  • CRT free: the call reached immediately after the direct caller of ExpressionToPostfix.
  • SYM_INVALID: the postfix terminator immediate found inside ExpandExpression.

Before calling ExpressionToPostfix, the evaluator scans the UTF-16 expression and marks identifiers for variable resolution. It skips quoted strings and identifiers that follow a ., so member expressions such as Point(1,2).x are left alone. After postfix generation, FindOrAddVar resolves variables and function references, FinalizeExpression runs when the build has a separate function, and ExpandExpression evaluates the result.

#Include ahk_hack_single.ahk
AhkMagic.Init()

MsgBox AhkMagic.EvalNative("1 + 2 * 3")          ; 7
MsgBox AhkMagic.EvalNative("2 * 3.5")            ; 7.0
MsgBox AhkMagic.EvalNative("Abs(-5)")            ; 5
MsgBox AhkMagic.EvalNative("SubStr(`"abc`", 2)") ; "bc"

myVar := 42
MsgBox AhkMagic.EvalNative("myVar + 1")          ; 43

The verified builds support literals, operators, globals, and function calls. Unsupported input raises an error with the pipeline status.

6. EvalScript: long text, functions, and classes

Expression evaluation cannot define functions or classes. EvalScript() uses the interpreter's include machinery instead: write the text to a temp file, call OpenIncludedFile, load it with LoadIncludedFile(TextStream*), run PreparseExpressions on the new lines, and call PreprocessLocalVars for each new function. The last non-declaration line is then evaluated with EvalNative().

Each entry point is located at runtime:

  • PreparseExpressions is found through callers of ExpressionToPostfix combined with cmp byte ptr [rbx], 3/4 patterns.
  • PreprocessLocalVars uses its movzx plus cmp byte ptr [rax+0x23], 2 signature.
  • OpenIncludedFile uses two prologue needles covering the 2.0 line and 2.1.
  • LoadIncludedFile(TextStream*) is found through a cmp eax,3 site in the callers of OpenIncludedFile.
  • Line::sSourceFileCount is discovered from a backward RIP-relative load with a plausible small count.
  • The g global is discovered inside callers of PreparseExpressions via a mov rax,[rip+disp] followed by a store into offset 0x28.

The script state is saved before loading and restored in a finally block: pending parent/related lines, pending parameter initializers, current module, expression-function state, and class count. This keeps temporary parser state out of the caller.

script := "
(
add(a, b) {
    return a + b
}
add(1, 2)
)"
MsgBox AhkMagic.EvalScript(script)               ; 3

classScript := "
(
class Point {
    x := 0
    y := 0
    __New(x, y) {
        this.x := x
        this.y := y
    }
}
Point(1, 2).x
)"
MsgBox AhkMagic.EvalScript(classScript)          ; 1

7. Runtime discovery versus layout constants

"Hardcoded" needs a precise definition here. The library has no per-version table of function RVAs or global addresses. Tables, function entry points, globals, and enum values are discovered at runtime. What remains per-version is a small set of C++ struct field offsets for Script, ScriptModule, UserFunc, Line, ArgStruct, and expression tokens.

Axis Status
Table addresses (g_BIF, sMdFunc, g_BIV_A) Runtime-discovered by PE and signature scan
Function entry points (EvalNative and EvalScript pipelines) Runtime-discovered, no RVA table
Globals (g, gScript, current-line slot, sSourceFileCount) Runtime-discovered
Enum values such as SYM_INVALID Runtime-discovered by the internal locator
C++ struct field offsets (Script, ScriptModule, UserFunc, Line, ArgStruct, tokens) Per-version layout constants, validated by the test matrix

Field offsets are a different axis from addresses. They describe how members sit inside C++ objects, and they are exercised by the four-build test matrix. A build whose layout differs will make the probes fail explicitly.

The optional cnumpy bridge applies the same idea to AHK Array objects. AhkLayout discovers mItem, mLength, mCapacity, and the Variant layout by diffing live objects, then cross-validates with a second independent probe set.

8. Complete examples

8.1 Table inventory

#Include ahk_hack_single.ahk
AhkMagic.Init()

MsgBox AhkMagic.Summary()
for name, info in AhkMagic.bif {
    if name = "Abs" or InStr(name, "Str")
        MsgBox name " rva=0x" Format("{:X}", info["rva"])
}

8.2 Generic export scan

hmod := DllCall("GetModuleHandle", "Str", "kernel32.dll", "Ptr")
exports := AhkMagic.ScanExports(hmod)
for name in ["VirtualAlloc", "CreateFileW", "ReadProcessMemory"] {
    if exports.Has(name)
        MsgBox name " rva=0x" Format("{:X}", exports[name]["rva"])
}

8.3 Built-in redirection, table and object

old := AhkMagic.PatchBif("Abs", "Sin")
name := "Abs"
MsgBox %name%(1)              ; dynamic lookup now returns sin(1)
AhkMagic.RestoreBif("Abs", old)

state := AhkMagic.PatchBifObject(Abs, "Sin")
MsgBox Abs(1)                 ; direct call now returns sin(1)
AhkMagic.RestoreBifObject(Abs, state)

PatchBif changes the table slot used by future dynamic lookups. PatchBifObject additionally rewrites the already-resolved function object's C function pointer, so a direct Abs(1) in source is redirected too. Both are restored in the example.

8.4 Expression eval

MsgBox AhkMagic.Eval("1 + 2 * 3")                  ; 7
MsgBox AhkMagic.Eval("StrLen(`"hello`")")            ; 5
MsgBox AhkMagic.EvalNative("Abs(-5)")                ; 5, in-process
MsgBox AhkMagic.EvalSubprocess("Format(`"{:.2f}`", Sin(1))")

10. Debugging and failure modes

  • 0xC0000005 usually means a wrong pointer or struct offset. Isolate the probe, record the version, and verify every located address before dereferencing it.
  • 0xC0000374 can happen when parser state is saved or restored in the wrong order. The project hit it during development; the fix was to restore every touched Script field in a finally block.
  • A "X not found" error means a locator signature did not match. That is intentional: unsupported builds fail instead of continuing with a guessed address.
  • Executable allocation and internal calls can be flagged by antivirus or EDR. Test in a VM, use a disposable interpreter, and keep a backup of the analyzed exe.

11. Security and usage rules

This library allocates executable memory, executes machine code, and reads or writes interpreter internals directly. Treat it as a reverse-engineering research tool.

Operations fall into three categories:

  • Read-only: Init, Summary, BifRva, BifAddr, ScanExports. These do not modify process state.
  • Mutating: PatchBif and RestoreBif. Wrong usage can crash the interpreter.
  • Executing: Eval, EvalNative, and EvalScript. This is arbitrary code execution in the current process.

Rules that apply to every experiment:

  • Never evaluate untrusted input.
  • Restore every PatchBif; do not leave redirection enabled.
  • Run the full test suite against the exact target exe before relying on a new build.
  • 32-bit AutoHotkey is not supported and raises an explicit error.
  • Only analyze software you are authorized to research. This is not a tool for bypassing licensing, DRM, or access controls.

12. Learning path

  1. Read a PE primer and inspect a real exe with ahk_inspect.py before touching the AHK side.
  2. Trace scanner.c: sections, pointer invariants, sorted runs, anchor names.
  3. Rebuild the machine code and verify the diff is empty.
  4. Study inproc_eval.c and the temporary Line/ArgStruct/ResultToken layout.
  5. Study EvalScript: save, load, preparse, preprocess, evaluate, restore.
  6. Read the AHK v2 source structures in the layout table (Script, ScriptModule, UserFunc) and correlate them with the test matrix.
