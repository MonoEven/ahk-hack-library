[b]AutoHotkey 运行时扫描库（ahk-hack）[/b]

仓库：[url=https://github.com/MonoEven/ahk-hack-library]https://github.com/MonoEven/ahk-hack-library[/url]

在线双语版本：[url=https://monoeven.github.io/ahk-hack-library/]https://monoeven.github.io/ahk-hack-library/[/url]

这个库解决一个问题：让 AutoHotkey 脚本在运行时读取正在运行的[c]AutoHotkey.exe[/c]，定位解释器内部表，并在此基础上提供内置函数重定向、表达式求值和远程 Hook。实现方式是往一个 AHK v2 文件里嵌入 x64 机器码，运行时解析 PE 结构并扫描内部结构。


[b]1. 运行时扫描[/b]

AutoHotkey 2 解释器在[c].data[/c]段维护几张关键表：

- [c]g_BIF[/c]：内置脚本函数表（[c]Abs[/c]、[c]Sin[/c]等），x64 下每条记录 0x20 字节；
- [c]sMdFunc[/c]：带类型签名的原生函数表（[c]MsgBox[/c]、[c]WinActivate[/c]等），0x28 字节；
- [c]g_BIV_A[/c]：以[c]A_[/c]开头的内置变量表（[c]A_AhkPath[/c]、[c]A_YYYY[/c]等），0x18 字节。

定位分两步。先解析 DOS 头、NT 头、节表，拿到各段内存范围；再检查[c].data[/c]和[c].rdata[/c]里的指针槽，看是否满足三个条件：名字指针指向 UTF-16 字符串、函数指针落在[c].text[/c]、表内记录按字典序排列。满足条件的连续记录区就是目标表，随后读出每条记录的 RVA、参数个数和 ID。

这套逻辑写进机器码后，同一段代码在全部 19 个已验证运行时构建（2.0-beta.9 到 2.1-alpha.30）上不加改动地运行。通用化之后还能扫任意 DLL/EXE 的导出表，枚举具名导出、RVA 和序号。


[b]2. 机器码生成[/b]

机器码用 C 编写，经 clang 编译后从 COFF 对象的[c].text[/c]段提取，再以十六进制字符串嵌进 AHK：

[codebox=text file=mcode-build]
clang -c -O2 -target x86_64-pc-windows-msvc -ffreestanding \
  -fno-builtin -fno-stack-protector -fno-unwind-tables \
  -fno-asynchronous-unwind-tables -fno-jump-tables scanner.c
[/codebox]

构建脚本会检查[c].text[/c]的重定位，只要有重定位逃出代码块就拒绝嵌入。这样保证嵌入结果是自包含、位置无关的机器码。

机器码部分包含以下代码块：

- [c]scanner.c[/c]：解释器三张内部表扫描；
- [c]export_scanner.c[/c]：通用 PE 导出表扫描；
- [c]inproc_eval.c[/c]：进程内表达式求值；
- [c]internal_locator.c[/c]：EvalNative 内部符号的运行时发现；
- [c]mem_script.c[/c]：EvalScript 的内存[c]TextStream[/c]；
- [c]remote_call_stub.c[/c]：远程线程调用 stub；
- [c]remote_eval_stub.c[/c]：远程表达式求值 stub。

重新构建机器码需要 LLVM clang（本机在[c]F:\Tech\LLVM\bin\clang.exe[/c]）：

[codebox=text file=rebuild]
python tools\build_mcode.py --embed-only --out ahk_hack_single.ahk
[/codebox]

扫描核心被提炼成一个文件：[c]ahk_hack_single.ahk[/c]。它包含[c]MCode()[/c]、[c]AhkMagic[/c]和全部嵌入的机器码，复制到哪里都能用。仓库里另有一个[c]ahk_hack_demo.ahk[/c]，直接运行就能看到扫描摘要、内置函数替换和 Eval 的效果。

[b]4. 基础用法：扫描与重定向[/b]

[color=#BF4000][b]4.1 核心扫描[/b][/color]

[codebox=autohotkey file=single-file-core-usage]
#Include ahk_hack_single.ahk

AhkMagic.Init()
MsgBox AhkMagic.Summary()

absRva  := AhkMagic.BifRva("Abs")
absAddr := AhkMagic.BifAddr("Abs")

hmod := DllCall("LoadLibraryW", "Str", "D:\path\module.dll", "Ptr")
exports := AhkMagic.ScanExports(hmod)
MsgBox exports.Count
[/codebox]

[color=#BF4000][b]4.2 内置函数重定向[/b][/color]

[codebox=autohotkey file=built-in-pointer-replacement]
#Include ahk_hack_single.ahk

old := AhkMagic.PatchBif("Abs", "Sin")
name := "Abs"
MsgBox %name%(1)              ; 表指针替换：动态调用返回 sin(1)

state := AhkMagic.PatchBifObject(Abs, "Sin")
MsgBox Abs(1)                 ; 深替换：源码里的直接调用也返回 sin(1)
AhkMagic.RestoreBifObject(Abs, state)
AhkMagic.RestoreBif("Abs", old)
[/codebox]

表指针替换影响后续动态查找；深替换直接改写已解析函数对象的 C 函数指针，所以脚本里写死的[c]Abs(1)[/c]也会变成[c]sin(1)[/c]，还原后恢复为 1。

[b]5. 进程内 Eval[/b]

[color=#BF4000][b]5.1 表达式求值[/b][/color]

[codebox=autohotkey file=eval-usage]
#Include ahk_hack_single.ahk

MsgBox AhkMagic.Eval("1 + 2 * 3")          ; 7
MsgBox AhkMagic.Eval("StrLen(`"hello`")")   ; 5
MsgBox AhkMagic.EvalSubprocess("Format(`"{:.2f}`", Sin(1))") ; 显式子进程
MsgBox AhkMagic.EvalNative("1 + 2 * 3")     ; 7，同进程
MsgBox AhkMagic.EvalNative("2 * 3.5")       ; 7.0，同进程
MsgBox AhkMagic.EvalNative("Abs(-5)")       ; 5，同进程
[/codebox]

[c]EvalNative[/c]构造临时[c]Line[/c]/[c]ArgStruct[/c]，直接调用当前进程里解释器自己的[c]ExpressionToPostfix[/c]和[c]ExpandExpression[/c]。全部 19 个已验证构建上都支持字面量、运算符、全局变量与函数调用；不支持的语法会直接报错。[c]Eval[/c]先走同进程管线，需要时再使用[c]EvalSubprocess[/c]。对象也能求值：裸函数名返回活着的[c]Func[/c]对象、类名返回[c]Class[/c]对象，因此[c]EvalNative("Abs")[/c]可以直接拿来用。

[color=#BF4000][b]5.2 函数定义[/b][/color]

[codebox=autohotkey file=evalscript-function]
#Include ahk_hack_single.ahk

script := "
(
add(a, b) {
    return a + b
}
add(1, 2)
)"
MsgBox AhkMagic.EvalScript(script)          ; 3，同进程
[/codebox]

[color=#BF4000][b]5.3 类定义[/b][/color]

[codebox=autohotkey file=evalscript-class]
#Include ahk_hack_single.ahk

classScript := "
(
class Point {
    x := 0
    y := 0
    __New(x, y) {
        this.x := x
        this.y := y
    }
}
Point(1, 2).x
)"
MsgBox AhkMagic.EvalScript(classScript)     ; 1，类定义并实例化
MsgBox AhkMagic.EvalNative("Point(1, 2).y") ; 2，类已加载并在进程内使用
[/codebox]

[c]EvalScript[/c]加载脚本文本本身不写临时[c].ahk[/c]文件：它把文本编码成 UTF-16，在 scratch 缓冲区里构造[c]TextMem[/c]兼容的[c]TextStream[/c]，直接交给[c]LoadIncludedFile(TextStream*)[/c]，所以函数定义和类定义都能在进程内生效。注入前会先用解释器自己的[c]/validate[/c]开关做语法预检（见 8.2 节），语法错误会携带真实的解析信息变成干净的库错误，而不是杀掉宿主进程；验证子进程静默运行并自行捕获输出，超时即杀掉整个进程树，不会在屏幕上留下对话框；只有这次预检使用临时文件，用后即删。

[color=#BF4000][b]5.4 原理[/b][/color]

[c]为什么这样就能 Eval：[/c]AutoHotkey 不会直接求值表达式字符串。脚本加载时，[c]Line::ExpressionToPostfix[/c]把每个表达式编译成后缀[c]ExprTokenType[/c]数组，[c]PreparseExpressions[/c]在加载期预编译表达式行，[c]PreprocessLocalVars[/c]绑定局部变量，最后[c]Line::ExpandExpression[/c]执行后缀。[c]EvalNative()[/c]构造同样的临时[c]Line[/c]/[c]ArgStruct[/c]并调用这些函数，所以复用的是解释器自己的语法和求值语义。[c]EvalScript()[/c]则通过内存[c]TextStream[/c]喂给同一条[c]LoadIncludedFile(TextStream*, int)[/c]管线；解析器不知道文本来自磁盘还是合成流，这就是函数和类能在进程内生效的原因。

[c]动态获取原理：[/c]稳定错误字符串在每次构建里都由 RIP 相对的[c]lea[/c]指令引用，扫描这些交叉引用并回退到函数开头就能得到函数地址；全局变量也用同样方式物化。布局偏移则让运行中的解释器自己暴露：一次性探针加载一个临时函数，diff 存活[c]Script[/c]对象得到[c]mFuncs[/c]/[c]mFuncsCount[/c]/[c]mLastLine[/c]，沿新函数的行链找到[c]mJumpLine[/c]，再从[c]LoadIncludedFile[/c]的[c]cmp[/c] prologue 读取解析器状态锚点。[c]TextStream[/c]对象同时填充两个[c]mData[/c]区域，不需要选择布局；每次加载再以结果验证（[c]rc == 1[/c]，探针加载还要函数计数增加），布局不同的构建会在探针阶段显式报错而不是错解析文本。

[c]多版本兼容：[/c]完整矩阵用同一份 blob 跑本机全部 19 个运行时构建——[c]2.0-beta.9[/c] 到 [c]2.1-alpha.30[/c] 加两个本机开发副本——每个运行时都通过全部十三项测试。不再信任任何解释器布局：eval blob 的每项 [c]Line[/c]/[c]ArgStruct[/c]/token/[c]DerefType[/c] 偏移与 token stride 都来自调用方传入的 21 槽布局数组，进程内由探针函数推导、远程从目标存活内存中发现；其余字段按已知探针文本内容匹配；解析器状态保存/恢复集合来自自动校验的候选区域，而不是按版本查表。内存 [c]TextStream[/c] 同时填充两个已知 [c]mData[/c] 槽，且每次加载都以结果验证。无法识别的布局会让探针抛错，不猜测偏移，失败因此是显式且隔离的。

[codebox=text file=source-snippets]

[b]6. 远程 Hook[/b]

目标不需要[c]#Include[/c]、导出指针或回调。附加端读取它的内存地图，定位解释器对象，并通过系统远程线程 API 启动一个远程线程。

[color=#BF4000][b]6.1 外部扫描工具[/b][/color]

[c]tools\ahk_remote_attach.py[/c]可以在不注入的情况下按 PID 或映像名读取目标进程：用[c]ReadProcessMemory[/c]读取 PE 头和 data 节，复用同一套锚点和连续记录扫描，直接报告三张内部表；也可以改写运行中的内置函数表，或在目标进程内执行表达式。

[codebox=text file=remote]
python tools\ahk_remote_attach.py --pid 1234 --filter Abs,MsgBox,AhkPath
python tools\ahk_remote_attach.py --name AutoHotkey64.exe --redirect Abs Sin
python tools\ahk_remote_attach.py --name AutoHotkey64.exe --eval "1 + 2 * 3"
[/codebox]

[color=#BF4000][b]6.2 AHK Hook API[/b][/color]

[c]AttachRemoteByName("AutoHotkey64.exe")[/c]按映像名找到运行中的目标进程，用[c]OpenProcess[/c]打开，用[c]ReadProcessMemory[/c]读取 PE 头和 data 节，扫描锚点名和连续排序记录定位三张表，返回包含[c]image_base[/c]、[c]table_rva[/c]和条目的 Map。[c]AttachRemote(pid)[/c]是同一套扫描的 PID 形式。

[c]RemoteRedirect(hook, "Abs", "Sin")[/c]以写权限重新打开目标，把目标函数指针写进源条目对应的[c]fn_ptr[/c]槽。[c]RemoteDeepRedirect(hook, "Abs", "Sin")[/c]再深一层：扫描目标堆里已经解析出来的[c]Func[/c]对象，改写它的[c]mBIF[/c]。这样像[c]B()[/c]直接调用[c]A()[/c]的函数也会跟着变化。

[color=#BF4000][b]6.3 热键验证[/b][/color]

远程改的是另一个进程的内存，验证时需要让目标自己把结果写出来。目标脚本[c]tests\remote_hook_resident_target.ahk[/c]保持常驻，[c]F7[/c]输出动态调用[c]%name%(1)[/c]，[c]F8[/c]输出全局变量[c]x[/c]；挂载脚本[c]tests\remote_hook_resident_demo.ahk[/c]每做一步 Hook 就向目标发送对应热键。

[codebox=autohotkey file=remote-hook-attacher]
#Include ahk_hack_single.ahk

; Attacher：tests\remote_hook_resident_demo.ahk
F1:: {
    global hook
    hook := AhkMagic.AttachRemoteByName("AutoHotkey64.exe")
}
F2:: {
    global hook
    AhkMagic.RemoteRedirect(hook, "Abs", "Sin")
    Send "{F7}"          ; 触发目标热键校验
    Sleep 400
}
F3:: {
    global hook
    AhkMagic.RemoteEval(hook, "x := 1 + 2 * 3")
    Send "{F8}"          ; 触发目标热键校验
    Sleep 400
}
[/codebox]

[codebox=autohotkey file=remote-resident-target]
; 常驻目标：tests\remote_hook_resident_target.ahk
#NoTrayIcon
Persistent

pidFile := A_Temp "\ahk_remote_attach_target.pid"
outFile := A_Temp "\ahk_remote_resident.out"
errFile := A_Temp "\ahk_remote_resident.err"
try FileDelete(outFile)
try FileDelete(errFile)
FileAppend(DllCall("GetCurrentProcessId") "`n", pidFile)

x := 0
name := "Abs"

F7:: {
    global name
    global outFile
    try {
        FileAppend("f7=" %name%(1) "`n", outFile)
    } catch as e {
        FileAppend("f7err=" e.Message "`n", outFile)
    }
}

F8:: {
    global x
    global outFile
    FileAppend("f8=" x "`n", outFile)
}
[/codebox]

启动目标脚本，先按[c]F1[/c]挂载，再按[c]F2[/c]把[c]Abs[/c]重定向为[c]Sin[/c]。目标收到[c]F7[/c]后写出[c]0.8414709848078965[/c]（即[c]Sin(1)[/c]），原来是[c]1[/c]。按[c]F3[/c]远程执行[c]x := 1 + 2 * 3[/c]，目标收到[c]F8[/c]后写出[c]7[/c]。

[color=#BF4000][b]6.4 RemoteEval[/b][/color]

[c]RemoteEval(hook, expr)[/c]把内部定位器和表达式求值 blob 连同一个小型线程 stub 写进目标进程，用[c]CreateRemoteThread[/c]执行，再读回结果。[c]1 + 2 * 3[/c]、[c]2 * 3.5[/c]这类基础表达式已远程验证；字符串字面量和返回字符串的内置调用（如[c]SubStr[/c]、[c]Format[/c]）也能正确读回。对象无法跨进程传递：[c]RemoteEval(hook, "Add")[/c]返回目标进程内对象地址（整数）。如果注入的求值挂起，调用会在 10 秒后超时并抛出清晰错误，同时有意泄漏注入块——释放目标仍在执行的内存会把它打崩（见 8.3 节）。

目标进程不需要任何特殊代码：不需要[c]#Include[/c]、不需要导出指针、不需要回调，也不需要内嵌元数据。测试脚本里写 PID 文件只是测试编排用的，[c]tools\ahk_remote_attach.py --name AutoHotkey64.exe[/c]可以直接按映像名解析 PID。

函数到函数的验证：[c]tests\remote_hook_function_target.ahk[/c]定义了[c]B_direct()[/c]（直接调用[c]Abs[/c]）和[c]B_dynamic()[/c]（动态调用[c]%name%[/c]）。[c]tests\remote_hook_function_demo.ahk[/c]深补丁[c]Abs -> Sin[/c]并触发两个热键，两个输出都变成[c]0.8414709848078965[/c]。

[color=#BF4000][b]6.5 RemoteEvalScript[/b][/color]

[c]RemoteEvalScript(hook, text)[/c]通过目标自己的脚本加载管线在目标里加载多行脚本。注入线程会在[c]PreparseExpressions[/c]前设置[c]g->CurrentFunc[/c]，所以函数和 class 定义都能正常工作。布局发现需要活的函数条目来校验，因此对脚本里没有任何用户函数的目标，会先经目标自己的加载器注入两个随机命名的探针函数并对其 preparse，再重试发现（见 8.5 节）——挂到全新空脚本上也能直接工作。

[codebox=autohotkey file=remote-eval-script]
#Include ahk_hack_single.ahk

hook := AhkMagic.AttachRemoteByName("AutoHotkey64.exe")

script := "
(
add(a, b) {
    return a + b
}
add(1, 2)
)"
MsgBox AhkMagic.RemoteEvalScript(hook, script)   ; 3
[/codebox]

[color=#BF4000][b]6.6 函数体替换与类验证[/b][/color]

热键校验采用和[c]Abs -> Sin[/c]一样的地址替换。[c]tests\remote_hook_evalscript_target.ahk[/c]定义[c]B_add(x)[/c]直接调用[c]A(x)[/c]，[c]F9[/c]输出[c]B_add(1)[/c]；[c]tests\remote_hook_evalscript_demo.ahk[/c]在[c]F2[/c]加载[c]NewA[/c]，用[c]RemoteReplaceFuncBody("A", "NewA")[/c]替换[c]A[/c]的函数体地址，再发送[c]F9[/c]。

[codebox=autohotkey file=remote-eval-script-target]
; 常驻目标：tests\remote_hook_evalscript_target.ahk
A(x) {
    return 1
}
B_add(x) {
    return A(x)
}
F9:: FileAppend("f9=" B_add(1) "`n", A_Temp "\ahk_remote_evalscript.out")
[/codebox]

[codebox=autohotkey file=remote-eval-script-attacher]

; Attacher：tests\remote_hook_evalscript_demo.ahk

    (
    NewA(x) {
        return 42

[b]8. 鲁棒性与失败行为[/b]

库把自身的输入和目标进程的内存都当作不可信数据，所有失败模式都设计成显式报错而不是静默出错。

[color=#BF4000][b]8.1 读取校验[/b][/color]

[c]Init()[/c]与[c]ScanExports()[/c]按扫描器输出契约封顶记录数（512/512/256 与 4096 条）、校验表步长，并在解引用前对每个名字指针做内存映射检查。超出契约的运行时会得到明确的[c]unsupported interpreter layout[/c]错误而不是越界读取；Init 失败会重置自身状态，下次调用可干净重试。机器码扫描器同步加固：导出子表指针与序号按镜像边界校验、节尾用[c]SizeOfImage[/c]封顶、字符串扫描在节边界处停止。

[color=#BF4000][b]8.2 语法预检[/b][/color]

解释器自己的加载器遇到语法错误会中止整个进程，库无法捕获。因此[c]EvalScript()[/c]与[c]RemoteEvalScript()[/c]在注入前先用解释器自己的[c]/validate[/c]开关预检文本——远程路径使用目标自己的可执行文件。语法错误现在会在触碰任何解释器状态之前变成携带真实解析信息的干净库错误，宿主或目标进程保持存活。验证命令经由无 BOM 的批处理文件传递（AHK 的[c]Run[/c]会重新解析嵌套引号、可能悄悄丢掉开关），库以捕获输出加完成标记文件来驱动验证器，而不是依赖进程退出码：错误文本一落盘就杀掉整个验证器进程树并抛出真实解析信息，任何构建都不会在屏幕上留下对话框；清理竞态被吞掉，被锁的临时文件不会掩盖真实错误。个别版本才有的语义加载警告会被容忍，因此引用宿主/目标中已有名字的合法脚本照常加载。

[color=#BF4000][b]8.3 远程超时[/b][/color]

挂起的表达式无法被安全杀死：终止一个正处在解释器内部的注入线程会损坏目标进程。[c]RemoteEval()[/c]与远程调用辅助函数等待 10 秒后抛出清晰的超时错误，并有意泄漏注入块，而不是释放目标可能仍在执行的内存。目标进程继续运行；代价是每次超时一个有界的 8 MiB 分配。

[color=#BF4000][b]8.4 对象返回值[/b][/color]

求值裸名字现在返回对象而不是“unknown type”错误：[c]EvalNative("Abs")[/c]返回活着的[c]Func[/c]对象，求值类名返回[c]Class[/c]对象。远程求值无法让对象跨进程，因此[c]RemoteEval(hook, "Add")[/c]返回对象在目标进程内的地址（整数），供远程原语继续使用。

[color=#BF4000][b]8.5 空目标与布局探针[/b][/color]

远程布局发现需要活的函数条目来校验，脚本里没有用户函数的目标过去会报[c]dynamic function layout not found[/c]。[c]RemoteEvalScript()[/c]现在会经目标自己的加载器注入两个随机命名的探针函数，preparse 后重试发现，挂到全新空脚本也能工作。探针名随机化以避免与用户代码冲突。

[color=#BF4000][b]8.6 补丁原子性[/b][/color]

补丁提交方式保证失败时不会留下半应用状态：[c]PatchBifObject()[/c]先改表再改对象、对象写入失败时回滚表；[c]RemoteDeepRedirect()[/c]写入前为每个槽位做快照、后续写入失败时恢复已写槽位，并用 vtable/布局检查收窄堆扫描避免误伤无关结构。进程内布局探针在[c]finally[/c]块中恢复解释器快照，发现失败不再残留临时函数。


[b]9. 安全性[/b]

[color=#BF4000]这个库会在你的进程里分配可执行内存、执行机器码，并直接读写解释器内部结构。请按逆向工程研究工具的标准来使用。[/color]

[c]Eval 安全吗？不安全。[/c][c]Eval[/c]、[c]EvalNative[/c]、[c]EvalScript[/c]会在当前进程以宿主脚本相同的权限执行任意代码，不具备沙箱隔离。进程内路径还会伪造解释器对象，布局错误或状态保存失误可能直接损坏内存，并且不会抛出干净异常。远程 API 等价于在另一个 AutoHotkey 进程里执行同样的操作。

操作分三类：

- 只读：[c]Init / Summary / BifRva / BifAddr / ScanExports / AttachRemote[/c]，不修改进程状态，主要风险在兼容性；
- 修改：[c]PatchBif / RestoreBif / RemoteRedirect / RemoteDeepRedirect / RemoteReplaceFuncBody[/c]，直接改内存里的内部结构，写错会崩溃。开发中实际遇到过[c]0xC0000374[/c]（堆损坏）；
- 执行：[c]Eval / EvalNative / EvalScript / RemoteEval / RemoteEvalScript[/c]，等价于运行任意脚本。

需要留意的风险：

- 可执行内存分配和内部函数调用可能被杀毒软件或 EDR 标记；
- 全部函数入口、全局量和布局偏移均在运行时定位，没有按版本表；仍需在目标 exe 上跑测试确认；
- [c]PatchBif[/c]和远程重定向用完必须还原，不要长期保留；
- 不要 eval 未受信任的输入；
- 32 位版本会显式报错。

建议在虚拟机或隔离环境里验证，备份被分析的 exe 并记录 SHA256。这个库不用于绕过授权、DRM 或访问控制。

- 内存 [c]TextStream[/c] 保留双 [c]mData[/c] 槽写入作为跨版本机制，每次加载以结果自校验（[c]rc == 1[/c] + 探针函数计数增量），不支持的布局在探针阶段显式报错；
- AhkLive 的 [c]Var[/c] 值/符号/标志字节改为 int→object 赋值差分发现，不再用固定偏移；
- 重写[c]_ValidateScript[/c]：验证命令经无 BOM 批处理文件传递，由捕获输出加完成标记文件驱动，错误文本一落盘立即杀树——语法错误永远以解释器的真实解析信息抛出，绝不弹窗；
- [c]FileDelete[/c] 统一加 [c]FileExist[/c] 守卫并吞掉清理竞态（不存在或被锁的临时文件不再挂起或掩盖错误）；
- 矩阵扩展到十三项测试（对象返回、语法错误存活、空目标探针注入、深重定向），19 个运行时全部 13/13。


[b]11. 已知限制[/b]

- 机器码块只支持 x64，32 位会显式报错；
- [c]EvalNative()[/c]通过解释器内部的同进程表达式管线执行，全部 19 个已验证构建上支持字面量、运算符、全局变量与函数调用。[c]Eval()[/c]在脚本模式和普通运行时编译出的 exe 里都能回退到[c]EvalSubprocess()[/c]；如果用[c]AUTOHOTKEYSC[/c]独立运行时作 base，则不支持[c]/script[/c]，需要单独验证；
- UPX/MPRESS 压缩已验证；第三方壳、VM 保护或真正的脚本加密仍需逐个目标验证；
- [c]PatchBif()[/c]和[c]RemoteRedirect()[/c]对已经缓存的函数对象不追溯生效，需要[c]PatchBifObject()[/c]/[c]RemoteDeepRedirect()[/c]；
- [c]RemoteReplaceFuncBody()[/c]要求源函数和目标函数都已加载进目标进程；
- [c]TraceFunction[/c]目前要求至少两个必选参数，并拒绝可选/ByRef 参数；
