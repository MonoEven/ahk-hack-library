[b]AutoHotkey 运行时扫描库（ahk-hack）：把 exe 变成可读的结构化文档[/b]

仓库：[url=https://github.com/MonoEven/ahk-hack-library]https://github.com/MonoEven/ahk-hack-library[/url]
cnumpy 实践集成：[url=https://github.com/MonoEven/cnumpy]https://github.com/MonoEven/cnumpy[/url]

[i]摘要：这个项目用嵌入 AHK v2 的 x64 机器码，在运行时扫描 AutoHotkey 可执行文件的内部结构，并在此基础上提供原生数组构造、内置函数重定向和表达式求值等能力。cnumpy 数组转换是验证这套扫描能力的实践集成，不是核心。[/i]

最初的目标听起来像“破解 autohotkey.exe”，但真正有价值的部分不是绕过什么，而是一套可复用的运行时结构扫描机制。解释器不是黑盒，它只是一份可以被程序自己读取的 PE 文件。扫描器负责把这份文件翻译成运行时地图，后续所有操作都建立在这张地图上。


[b]1. 核心能力：运行时扫描[/b]

AutoHotkey 2 解释器在 [c].data[/c] 段维护了几张关键表。扫描器先解析 DOS 头、NT 头和节表，再按结构不变式定位这些表：

- [c]g_BIF[/c]：内置脚本函数表（[c]Abs[/c]、[c]Sin[/c] 等），x64 每条 0x20 字节；
- [c]sMdFunc[/c]：带类型签名的原生函数表（[c]MsgBox[/c]、[c]WinActivate[/c] 等），0x28 字节；
- [c]g_BIV_A[/c]：以 [c]A_[/c] 开头的内置变量表（[c]A_AhkPath[/c]、[c]A_YYYY[/c] 等），0x18 字节。

定位不是靠猜偏移，而是验证三个不变式：名字指针必须指向 UTF-16 字符串、函数指针必须落在 [c].text[/c]、表内记录必须按字典序排列。满足这些条件的连续记录区就是目标表。扫描完成后，每条记录的 RVA、参数个数、ID 都会被读出。

同一段机器码可以在 2.0-beta、2.0.0、2.0.26、2.1-alpha 上运行，不需要为每个版本单独维护偏移。这套思路还被泛化成通用 PE 导出表扫描器：给定任意已加载 DLL/EXE 的基址，就能枚举全部具名导出及其 RVA 和序号。[c]cnumpy_ahk.dll[/c] 的 1027 个导出就是这样自动识别的。


[b]2. 机器码从哪里来[/b]

机器码不是手写汇编，而是用 C 编写、clang 编译、再从 COFF 对象的 [c].text[/c] 段提取的：

[codebox=text file=tools\build_mcode.py 摘要]
clang -c -O2 -target x86_64-pc-windows-msvc -ffreestanding \
  -fno-builtin -fno-stack-protector -fno-unwind-tables \
  -fno-asynchronous-unwind-tables -fno-jump-tables scanner.c
[/codebox]

构建脚本会检查重定位：只要有任何重定位逃出 [c].text[/c]，就拒绝嵌入。这保证嵌入 AHK 的是一段完全自包含、位置无关的代码。

库包含四个机器码块：

- [c]scanner.c[/c]：解释器三张内部表扫描；
- [c]export_scanner.c[/c]：通用 PE 导出表扫描；
- [c]array_builder.c[/c]：数值叶子节点的原生 Array 填充；
- [c]array_children_builder.c[/c]：父节点子引用填充。


[b]3. 库结构[/b]

[codebox=text file=库结构]
lib/
  init.ahk                  核心入口，只引入扫描层
  ahk_hack.ahk              MCode() + AhkMagic
  mcode/                    机器码 C 源码
  cnumpy/                   可选实践集成
    init.ahk
    ahk_layout.ahk          运行时 AHK 布局发现（无硬编码偏移）
    numpy.ahk
    cnumpy_bridge.ahk       CnpBridge + CnpView
tools/
  build_mcode.py            编译并嵌入机器码
  ahk_inspect.py            Python/PE 交叉验证
fork/cnumpy-ahk-bridge/     cnumpy 集成测试与基准
[/codebox]

根目录 [c]ahk_mcode.ahk[/c] 保留为一行兼容别名。


[b]4. 使用说明[/b]

[color=#BF4000][b]4.1 核心扫描[/b][/color]

[codebox=autohotkey file=lib\init.ahk]
#Include ahk_hack.ahk
[/codebox]

[codebox=autohotkey file=核心扫描用法]
#Include lib\init.ahk

AhkMagic.Init()
MsgBox AhkMagic.Summary()

absRva  := AhkMagic.BifRva("Abs")
absAddr := AhkMagic.BifAddr("Abs")

hmod := DllCall("LoadLibraryW", "Str", "D:\path\cnumpy_ahk.dll", "Ptr")
exports := AhkMagic.ScanExports(hmod)
MsgBox exports.Count
[/codebox]

[color=#BF4000][b]4.2 内置函数重定向[/b][/color]

[codebox=autohotkey file=内置函数指针替换]
old := AhkMagic.PatchBif("Abs", "Sin")
name := "Abs"
MsgBox %name%(1)              ; 首次动态调用返回 sin(1)
AhkMagic.RestoreBif("Abs", old)
[/codebox]

AHK 可能缓存已经解析过的函数对象，因此“首次动态调用反映新指针”是预期行为；表指针本身一定会被还原。

[color=#BF4000][b]4.3 表达式 Eval[/b][/color]

[codebox=autohotkey file=Eval 用法]
MsgBox AhkMagic.Eval("1 + 2 * 3")          ; 7
MsgBox AhkMagic.Eval("StrLen(`"hello`")")   ; 5
[/codebox]

[color=#BF4000][b]4.4 可选 cnumpy 集成[/b][/color]

先设置 DLL 路径，再引入集成入口：

[codebox=autohotkey file=lib\cnumpy\init.ahk]
Numpy.DllPath := "D:\...\build\x64\Release\cnumpy_ahk.dll"
#Include lib\cnumpy\init.ahk

meta := CnpBridge.Metadata(arr)
ahk  := CnpBridge.ToAhk(arr)
fast := CnpBridge.ToAhkFast(arr)
native := CnpBridge.ToAhkNative(arr)
view := CnpBridge.View(arr)
buf  := CnpBridge.ToBuffer(arr)

back1 := CnpBridge.FromAhk(ahk, dtype)
back2 := CnpBridge.FromAhkFast(ahk, dtype)
back3 := CnpBridge.FromBuffer(buf, dtype)
[/codebox]

[color=#BF4000][b]4.5 生命周期与所有权[/b][/color]

- 除 [c]CnpView[/c] 外的所有转换都是拷贝语义，AHK 与 cnumpy 各管各的内存；
- [c]CnpView[/c] 是零拷贝借用，持有对 Owner [c]NdArray[/c] 的强引用；view 和原引用都释放后数组才回收；
- view 写操作仅允许在数组可写（[c]CNP_ARRAY_WRITEABLE[/c]）时进行；
- 不要保存 [c]view.Ptr[/c] 到全局并在 view 释放后使用；
- 原生构造使用 [c]Array().Capacity := n[/c] 让解释器自己分配 [c]mItem[/c]，不要用外部 Buffer 顶替，否则退出时会双重释放。

完整规则见 [c]fork/cnumpy-ahk-bridge/docs/lifecycle-and-ownership.md[/c]。

[color=#BF4000][b]4.6 重新构建机器码[/b][/color]

需要 LLVM clang（本机在 [c]F:\Tech\LLVM\bin\clang.exe[/c]）：

[codebox=text file=重新构建]
python tools\build_mcode.py --embed-only --out lib\ahk_hack.ahk
[/codebox]

[b]5. 安全性（重要，请完整阅读）[/b]

[color=#BF4000]这个库会在你的进程里分配可执行内存、执行机器码，并直接读写解释器内部结构。请把它当作逆向工程研究工具，而不是普通脚本库。[/color]

操作分为三类：

- 只读：[c]Init / Summary / BifRva / BifAddr / ScanExports / Metadata / CnpView 读[/c]，不修改进程状态，主要风险是兼容性；
- 修改：[c]PatchBif / RestoreBif / WriteRaw / CnpView.Set[/c]，直接改内存中的内部表或数据，写错会崩溃。本项目开发中真实遇到 [c]0xC0000374[/c]（堆损坏）；
- 执行：[c]Eval[/c]，等价于任意脚本执行。

主要风险：

- 可执行内存分配与内部函数调用可能被杀毒软件或 EDR 标记；
- 偏移基于 AutoHotkey 2.0.26 源码推导，其他版本、编译器、架构可能不同，使用前必须对目标 exe 跑测试；
- 不要长期保留 [c]PatchBif[/c]，用完必须还原；
- 绝不 eval 未受信任输入；
- 不要违反 [c]CnpView[/c] 所有权规则；
- 不要用外部 Buffer 顶替 [c]mItem[/c]；
- 32 位不支持，[c]Init()[/c] 会显式报错。

建议在虚拟机或隔离环境验证，备份被分析的 exe 并记录 SHA256。本项目不用于绕过授权、DRM 或访问控制。


[b]6. 性能数据[/b]

[codebox=text file=100M 基准（QPC）]
count=100000000
Capacity only ms=0.059
ToAhkNative ms=705.448
ToBuffer ms=206.068
View create ms=0.0111
2D 1000x1000 ToAhkNative ms=14.892
2D 1000x1000 ToAhk old ms=466.479
[/codebox]

早期“1M 元素 < 1ms”是计时分辨率假象（[c]GetTickCount64[/c] 粒度 1ms）。用 QPC 测 100M 元素，原生构造约 705ms；2D 1000x1000 约 15ms，旧 AHK 路径约 466ms。


[b]7. 更新：修复 cnumpy 硬编码偏移（2026-08-11）[/b]

cnumpy 侧修复了写死偏移的问题，本库已同步更正：

- 移除 [c]CnpBridge[/c] 中写死的 [c]CnpArray[/c] 偏移（[c]_OFF_DATA=32[/c]、[c]_OFF_OFFSET=64[/c] 等）；
- 数据指针改由 [c]cnp_ahk_data_ptr[/c] 提供，dtype kind 改由 [c]cnp_dtype_kind[/c] 提供；
- [c]ToAhkNative[/c] 改用运行时发现的 [c]AhkLayout[/c] 和 cnumpy 原生填充器 [c]cnp_ahk_fill_array_flat[/c] / [c]cnp_ahk_fill_array_nd[/c]；
- 新增 [c]lib/cnumpy/ahk_layout.ahk[/c]，整个集成不再依赖任何写死的解释器或 CnpArray 布局。

验证：1D/2D/3D 原生构造、roundtrip、view 读写、所有权、cnumpy 未受影响，全部通过。


[b]8. 已知限制[/b]

- 机器码块仅支持 x64；
- [c]Eval()[/c] 通过同 exe 的隐藏子进程执行，返回字符串/数字；同进程 eval 仍需定位内部表达式解析器；
- [c]PatchBif()[/c] 不追溯已缓存函数对象；
- [c]ToAhkNative[/c] 要求 C 连续、数值类型；字符串/结构化 dtype 走旧路径；
- 原生构造依赖运行时布局发现，跨版本使用前必须验证。


[b]9. 结语[/b]

“破解 exe”最终变成了一个更干净的形态：把 exe 当作程序自身可以读取的结构化文档，扫描出内部地图，再在地图上做实验。cnumpy 集成是验证地图质量的试金石：它能把 100M 元素的转换从几十秒量级压到亚秒量级。核心价值始终是扫描。
